# 分析看板性能与缓存

## 1. 查询链路

看板运行时主要有两条查询：

1. **数据集原始查询**：用于筛选器候选值、设计器字段推断、未下推组件的兜底数据。
2. **组件级查询**：把组件的过滤、分组、聚合、排序、Top N 尽量下推到数据库。

前端 `useDashboardData` 会按 `datasetId + 聚合 + sort + limit + offset` 生成查询 key，
相同 key 的多个组件复用一次请求。

## 2. 服务端聚合

### 请求参数

`POST /api/analysis-dashboards/{id}/query`

```json
{
  "datasetIds": ["ds_sales"],
  "queries": [
    {
      "id": "q1",
      "datasetId": "ds_sales",
      "groupFields": ["region", "channel"],
      "aggregations": [
        { "field": "sales_amount", "agg": "sum" }
      ],
      "sortField": "sales_amount",
      "sortOrder": "desc",
      "limit": 100
    }
  ],
  "filterValues": {}
}
```

### SQL 构建

`DatasetAggregationSqlBuilder` 会把数据集原始/筛选 SQL 包成子查询：

```sql
SELECT *
FROM (
  SELECT region, channel, SUM(sales_amount) AS sales_amount
  FROM (<dataset_sql>) dp_agg
  GROUP BY region, channel
) dp_sort
ORDER BY sales_amount DESC
LIMIT 100
```

随后复用 `DatasetSortLimitSqlBuilder`，兼容 MySQL / PostgreSQL / SQL Server / Oracle 等方言。

### 返回标记

服务端完成聚合后会在结果中返回：

```json
{ "aggregated": true }
```

前端据此跳过客户端聚合，避免 `avg/count` 等指标被二次聚合。

### 筛选器统一服务端执行

所有筛选器都随查询请求发送到服务端：

- SQL 数据集直接字段：外层子查询追加 `WHERE` 条件。
- 指标数据集直接字段：解析为维度过滤条件。
- `pushdown` 目标：按声明执行 `metricTime / metricDimension / metricFactField / sqlParam`。

前端不再对返回行做本地过滤，因此筛选值变化一定会重新请求服务端。

### 占总比与 limit

`percentOfTotal` / `stackedPercent` 需要先基于完整聚合结果计算占比，再应用 `limit`。
因此这类组件不会把 `limit` 下推到服务端查询，前端会在占比计算完成后再截断显示。
这样 Top N 的占比仍以全量数据为分母，而不是以截断后的子集为分母。

## 3. 查询缓存

`DashboardDataService.queryWidgets` 对**已保存看板**的批量查询结果做内存缓存。

- 默认 TTL：30 秒
- 最大条目：256
- 淘汰策略：LRU
- 仅缓存成功结果；包含 `errors` / `widgetErrors` 的响应不缓存
- 设计页 `preview-query` 不缓存，避免未保存草稿互相污染

### 缓存 key

包含：

- dashboardId
- 排序后的 datasetIds
- 组件查询（含 groupFields / aggregations / sort / limit / offset）
- 排序后的 filterValues

### 失效

- 看板保存、更新、删除后主动清除该看板缓存
- `DashboardDataService#clearQueryCache()` 可清空全部缓存

## 4. 性能建议

- 大表图表优先使用 `encode.groupBy=true`，让分组聚合下推数据库。
- 透视表直接使用 `row/column/value`，无需先拉全量明细。
- 表格分页使用 `encode.pageSize`，服务端分页只返回当前页。
- 避免在同一个看板中给同一数据集配置大量不同 sort/limit，否则会生成多个查询。
- 所有筛选器均由服务端执行；前端不再按返回行做本地过滤。
- 时间范围筛选尽量使用 `metricTime` / `sqlParam` 下推。
- 大屏自动刷新间隔不建议低于 30 秒，避免缓存失效后频繁打库。
