# 1000 万行同步实测：DataY vs SeaTunnel，从落后 33% 到反超 40%

> 一次不太体面的性能对比，和一个只值一行的真相。

做数据同步工具的人，大概都有同一个心结：自己写的东西，到底比开源方案快还是慢？

我们也有。于是挑了一个最朴素、也最容易被用户拿来对比的场景——**MySQL 到 MySQL，1000 万行，约 2 GB，单机全量同步**——把 DataY 和 Apache SeaTunnel 放在同一台机器、同一个库、同一份数据上，跑了一遍。

结果第一轮就把我们打懵了：**DataY 比 SeaTunnel 慢了 33%**。

但这篇不是一篇「后来我们赢了」的爽文。真正值得写下来的，是中间那段排查——以及最后发现，差距的起点只是 JDBC 连接串里的一个参数。

---

## 先看结论

| 场景 | DataY | SeaTunnel 2.3.11 | 差距 |
|---|---|---|---|
| 单并发（1000 万行） | 102.3 s / 97,760 行/s | 120.8 s / 82,768 行/s | DataY 快 15% |
| 4 并发（1000 万行） | **46.9 s / 213,070 行/s** | 65.5 s / 152,607 行/s | **DataY 快 28%（吞吐 +40%）** |
| 4 并发并行效率 | 2.21× | 1.84× | — |
| 达到 MySQL 库内直搬上限的比例 | 65.6% | 47.0% | — |

而这一切的起点是：

| 单并发（修复前） | DataY | SeaTunnel | 差距 |
|---|---|---|---|
| 1000 万行 | 155.9 s / 64,150 行/s | 117.2 s / 85,330 行/s | DataY 慢 33% |

同一份代码，只改了一个连接参数，吞吐提升 52%。

---

## 一、先说测试怎么做

性能对比最怕「各说各话」，所以先把条件钉死。

**硬件与环境**

- Apple M5，10 核，24 GB 内存，macOS
- 源库、目标库、两个工具全部在本机（127.0.0.1 回环）
- MySQL 8.0.46 / 9.4.0，InnoDB buffer pool **仅 128 MB**，`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、binlog 开启
- JDK 17

注意这个配置：它比大多数生产库更"抠"。我们故意保留默认值，是想看两个工具在**同一条偏紧的 I/O 通道**上，谁更能把钱花在刀刃上。

**数据**

- 12 列：BIGINT 主键 + 订单号、客户名、手机、邮箱、地址、金额、数量、状态、备注、两个时间字段
- 1000 万行，物理大小 1800 MB，平均约 190 B/行

**对齐项**

- 并发度都是 1（或都是 4）
- 批量都是 10,000
- 都开 `rewriteBatchedStatements=true`
- 都流式读取、目标端 autocommit
- 每轮开始前 TRUNCATE 目标表
- 每轮结束校验 `COUNT(*)` 与 `SUM(amount)`，全部一致
- 两轮交叉跑（A→B→A→B），抵消缓存和运行顺序带来的偏差

SeaTunnel 用的是 **2.3.11**（当时最新稳定版）+ 官方 JDBC connector，不是 3.x。

## 二、第一回合：我们慢了 33%

| 方案 | 轮次 | 耗时 | 吞吐 | 峰值内存 |
|---|---|---|---|---|
| DataY | #1 | 156.219 s | 64,013 行/s | 2.7 GB |
| DataY | #2 | 155.555 s | 64,286 行/s | 2.8 GB |
| SeaTunnel | #1 | 117.855 s | 84,850 行/s | 1.0 GB |
| SeaTunnel | #2 | 116.534 s | 85,812 行/s | 1.6 GB |

组内波动都不到 1%，差距稳定复现。

**SeaTunnel 快 33%，内存还只有我们的一半。**

说不难受是假的。但工程师的本能是：先别改代码，先搞清楚时间花在哪了。

---

## 三、把问题切成三段

我们做了三个"对照实验"，每一步只回答一个问题。

### 第 1 问：数据库自己搬，要多久？

```sql
INSERT INTO dst SELECT * FROM src;
```

**30.2 秒，约 331,000 行/s。**

这是这台机器、这个 MySQL 配置下的"物理上限"。任何客户端工具都不可能比它更快——它连网络和序列化都省了。

### 第 2 问：DataY 只读不写，要多久？

把任务改成 `StreamJdbcInput → 空输出`：

**23.5 秒，424,835 行/s。**

读 1000 万行只花了 23.5 秒，而完整任务要 155.9 秒。

**结论很明确：读端没问题，慢在写端。**

### 第 3 问：那写端到底慢在哪？

我们写了一个 40 行的最小 JDBC 程序：读同样的表，批量 10,000，只切换目标连接的 `useServerPrepStmts`。

| 目标连接参数 | 200 万行耗时 | 吞吐 |
|---|---|---|
| `useServerPrepStmts=true` | 27.2 s | 73,597 行/s |
| `useServerPrepStmts=false` | 16.2 s | **123,792 行/s** |

**同一份代码、同一个库，只改这一个开关，吞吐差 68%。**

而且 73,597 这个数字，和我们完整任务的 64,150 几乎贴着——基本可以确认，元凶找到了。

---

## 四、真相：一个被"优化"坏了的参数

MySQL Connector/J 有一个众所周知的优化：`rewriteBatchedStatements=true`。

开启后，驱动会把 N 条 `INSERT ... VALUES (?,?)` 在客户端拼成**一条多值 INSERT**：

```sql
INSERT INTO t (a,b) VALUES (1,2),(3,4),(5,6),...
```

一次网络往返、一次解析、一次提交，批量写入的性能主要靠它。

但这里有个前提：**参数必须由客户端拼装**。

一旦开启 `useServerPrepStmts=true`，语句会被发送到服务端做预处理，参数也走服务端的绑定协议。此时批量重写失效，驱动退化成"逐条 prepare / 逐条 execute"——网络往返、SQL 解析、日志刷盘一个都省不掉。

而 DataY 的 MySQL 数据源里，恰好硬编码了：

```java
props.put("useServerPrepStmts", "true");
```

大概率是当初为了"用上服务端预编译"而加的，在单条查询场景确实有意义；但在**批量写入**场景，它把最关键的批量重写整没了。

改成 `false` 之后：

```java
// 必须使用客户端预编译：只有在客户端拼装参数时，
// rewriteBatchedStatements 才能把批量 INSERT 重写成单条多值语句。
props.put("useServerPrepStmts", "false");
```

## 五、第二回合：反超

改完重新跑，其他条件一个字没动。

| 方案 | 轮次 | 耗时 | 吞吐 |
|---|---|---|---|
| DataY（修复后） | #1 | 102.627 s | 97,440 行/s |
| DataY（修复后） | #2 | 101.543 s | 98,481 行/s |
| DataY（修复后） | #3 | 102.710 s | 97,362 行/s |
| SeaTunnel（同期复跑） | #1 | 119.066 s | 83,987 行/s |
| SeaTunnel（同期复跑） | #2 | 122.625 s | 81,549 行/s |

**155.9 s → 102.3 s，快了 34%；吞吐 64,150 → 97,760，提升 52%。**

不仅追平，还反超了 SeaTunnel 约 15%。内存也从 2.76 GB 降到 2.5 GB 左右——写入变快，管道里积压的批次自然就少了。

三轮结果落在 101.5–102.7 秒，波动 1.1%。

**这是一次典型的"默认值事故"：不是架构输了，是配置输了。**

## 六、第三回合：把并发拉到 4

单线程跑完，问题自然变成：多并发下还成立吗？

这里有个小插曲：SeaTunnel 的并行读需要 `table_path` 模式，而它 2.3.11 的 MySQL 方言只识别到 8.4，在 MySQL 9.4 上直接报 `Unsupported MySQL version: 9.4.0`。为了公平，我们另起了一个 MySQL 8.0.46 实例，用同一份脚本重建了 1000 万行、1800 MB、校验和完全一致的数据集，两边都在 8.0 上重测。

**单并发基线（8.0）**

| 方案 | 耗时 | 吞吐 |
|---|---|---|
| DataY | 103.9 s | 96,251 行/s |
| SeaTunnel | 120.5 s | 82,968 行/s |

和 9.4 上的结果吻合，说明换库不影响结论。

**4 并发（各跑 3 轮，交替执行）**

| 方案 | #1 | #2 | #3 | 平均 | 吞吐 |
|---|---|---|---|---|---|
| DataY | 49.3 s | 44.4 s | 47.1 s | **46.9 s** | **213,070 行/s** |
| SeaTunnel | 65.5 s | 63.9 s | 67.1 s | **65.5 s** | **152,607 行/s** |

**差距从 15% 扩大到 28%，吞吐领先 40%。**

扩展到 4 并发的效率：

| 方案 | 1 并发 | 4 并发 | 加速比 | 并行效率 |
|---|---|---|---|---|
| DataY | 96,251 | 213,070 | **2.21×** | 55.4% |
| SeaTunnel | 82,968 | 152,607 | 1.84× | 46.0% |

---

## 七、真正的天花板，不在客户端

4 并发之后，我们顺手测了数据库自己的极限：开 4 个会话，各搬 250 万行。

**30.8 秒，324,650 行/s。**

而单会话是 30.2 秒、331,000 行/s。

**几乎一模一样。**

这意味着：MySQL 服务端在 32 万行/s 左右就已经饱和，4 个写入连接只是在抢同一份 buffer pool、同一块盘、同一把 binlog 锁。客户端再怎么优化，也突破不了这个数。

于是有了这张更有意思的表：

| 方案 | 4 并发吞吐 | 占库内直搬上限 |
|---|---|---|
| 库内直搬（4 会话） | 324,650 行/s | 100% |
| DataY | 213,070 行/s | **65.6%** |
| SeaTunnel | 152,607 行/s | 47.0% |

DataY 已经吃掉了三分之二的天花板，SeaTunnel 还有一半空间没够到。

## 八、五条可以带走的经验

**1. 默认值会撒谎，基准测试不会。**

一个 `useServerPrepStmts=true`，能让批量写入慢一半。这类参数在单条 SQL 场景是优化，在批量场景就是灾难。做数据同步的工具，连接参数应该按"读"和"写"分别配置，而不是一套走天下。

**2. 性能问题先分段，别先改代码。**

"库内直搬 30 s → 只读 23.5 s → 完整 156 s"，三个数字一摆，问题范围就锁死在写端了。比盲猜快得多。

**3. 批量写入的关键是"减少往返"，不是"减少解析"。**

多值 INSERT 的本质是把 N 次 round-trip 压成 1 次。任何让驱动无法重写批量的配置，都会把这部分收益全部吐回去。

**4. 并发不是越高越好，先找到服务端饱和点。**

这台 MySQL 在 32 万行/s 就饱和了。4 并发时 DataY 已到 21 万，再加到 8 并发，收益大概率只剩个位数，代价却是锁竞争、复制延迟和内存翻倍。

**5. 内存也要算进成本。**

4 并发时 DataY 峰值 3.4 GB，SeaTunnel 2.8 GB。并发翻 4 倍，内存也接近线性上涨——容器里部署时，这是会真实 OOM 的。

---

## 九、必须说清楚的边界

一篇负责任的对比，得把"不能外推"的部分讲明白：

- **单机回环 + 128 MB buffer pool + binlog 全开**，绝对耗时不能代表生产环境。可以外推的是相对差距和瓶颈成因，不是"1000 万行只要 47 秒"。
- **SeaTunnel 是 2.3.11**，不是 3.x；它是基于 Spark/Flink 生态的成熟大数据引擎，在分布式、多源、Exactly-Once 等场景的能力远不是这个单机小测试能覆盖的。我们只比较了"单机 MySQL→MySQL 全量同步"这一个切面。
- **每组 2–3 轮**，没有做统计显著性检验；但组内波动 <1%，而差距在 15%–40%，远超噪声。
- **"单线程"指并行度为 1**，不是进程里只有一个 OS 线程。
- 4 并发测试为让 SeaTunnel 能并行读，使用了 MySQL 8.0.46；数据集与 9.4 上的完全一致（同样的行数、大小、校验和）。

## 写在最后

这次对比最让我们警醒的，不是"赢了 40%"，而是**第一轮那个 33% 的落后，来源只是一行配置**。

性能这件事，很少输在宏大的架构上，更多输在没人愿意回头看第二眼的默认值里。

所以这篇的标题虽然写着"反超"，但我们更想记住的是前半句：

> 我们本来准备认输。

## 关于 DataY

DataY 是一个「轻量但完整」的开源数据平台。它把数据集成、任务调度、维度建模、高性能数仓、分析看板、智能问数放进同一套运行时——**数据平台可以很小，功能不打折**。

**它和传统方案最大的不同，是"小"：**

- **一个 JAR 就能启动**，不依赖 Hadoop / Spark / 独立调度集群，没有"组件地狱"
- **2 核 4G** 的开发机，就能跑通「数据接入 → 数仓建模 → 报表 → 问数」的完整链路
- 零外部依赖，10 分钟搭好环境，不需要专职大数据团队维护

**但"轻量"指的是资源门槛，不是能力：**

- **数据集成**：自研流批一体引擎，支持 MySQL、Oracle、PostgreSQL、SQL Server、达梦、人大金仓、SAP HANA、Doris、ClickHouse、DuckDB、TDengine 等 20+ 数据源，以及 Iceberg / DuckLake / Apache Polaris 数据湖；支持全量、增量，以及 MySQL / PostgreSQL / Oracle / 达梦 / SQL Server 的 CDC 实时同步；可视化拖拽画布与 JSON 任务双模式；自动建表、字段变更同步、跨库数据比对
- **任务调度**：Quartz 精准到秒，DAG 工作流与嵌套工作流，失败重试、暂停恢复；调度 Master 与执行 Worker 可分离，单机能跑，集群能扩
- **高性能数仓**：内嵌 DuckDB，列存 + 向量化 + 无锁并发，单机跑出分布式数仓的性能；需要更大规模时可随时外挂 Doris / ClickHouse
- **分析看板**：拖拽式设计，16 种 ECharts 图表 + KPI / 明细表 / 透视表，支持下钻、筛选、大屏与 iframe 嵌入
- **AI 原生**：智能问数一句话出报表，AI 看板助手一句话生成看板，MCP Harness 让 Claude Desktop / Cursor 等 Agent 直接操作数据源、ETL 任务与指标

**本文的测试怎么跑起来的？**

用的就是 DataY 自带的 Core 引擎——一个 JSON 描述任务，命令行直接执行，没有额外部署任何东西：

```bash
java -jar datay-core/target/datay-core-*-jar-with-dependencies.jar taskConfig.json
```
