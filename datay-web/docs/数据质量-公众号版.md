# 任务成功了，数据就一定对吗？

> DataY 数据质量：把“靠人抽查”的数据校验，变成规则化、可执行、可追溯的数据任务

---

早上九点，日报准时发出来了。

同步任务显示成功，汇总任务显示成功，看板也能正常打开。

直到业务同学发来一句话：

> “昨天华东区的销售额，怎么比前天少了一半？”

继续往下查，问题往往不是某张表没同步，也不是哪个任务失败了，而是：

- 订单号有一批是空的；
- 金额字段出现了负数；
- 门店编码混进了测试数据；
- 某个枚举字段出现了系统不认识的状态；
- 订单表有数据，但商品维度表还没更新；
- 数据已经三天没更新，任务却一直是“成功”。

任务成功，只代表流程跑完了。

**数据是否正确、完整、及时，是另一件事。**

这就是数据质量要解决的问题。

## 01 数据质量，为什么总是“事后才知道”？

很多团队并不是不重视数据质量。

问题是，数据质量往往没有成为流程的一部分，而是散落在各个环节里。

### 1. 任务成功，不等于数据可用

数据同步任务的成功标准，通常是“数据写过去了”。

但写过去的数据可能是：

- 主键为空；
- 主键重复；
- 金额超出合理范围；
- 状态值不在枚举范围内；
- 日期字段格式错误；
- 表里只有 0 行；
- 数据停留在几天前；
- 字符串长度超出下游系统限制。

这些问题不会让同步任务报错，却会让下游报表、指标和模型“带病运行”。

### 2. 靠临时 SQL 抽查，覆盖少、效率低

最常见的做法是，出问题后临时写几条 SQL：

```sql
SELECT COUNT(*) FROM orders;

SELECT COUNT(*) FROM orders WHERE order_id IS NULL;

SELECT order_id, COUNT(*)
FROM orders
GROUP BY order_id
HAVING COUNT(*) > 1;
```

查完发现确实有问题，再把结果贴到聊天窗口里。

下次换一张表，再写一遍。

再下次换一个人，SQL 又换了一种写法。

问题是：

- 校验规则没有沉淀；
- 校验结果没有留存；
- 校验失败没有告警；
- 数据开发、测试、业务各查各的；
- 出了问题，很难证明“上次到底检查了什么”。

### 3. 数据链路越来越长，问题越来越晚发现

一条典型的数据链路可能是：

```text
业务库 -> ODS -> DWD -> DWS -> ADS -> 报表 / 指标 / 看板
```

数据每经过一层，问题就会被放大一次。

源库里一个空的订单号，到了汇总层可能变成一个错误的销售额；到了看板，可能变成一个完全离谱的结论。

越晚发现，修复成本越高。

### 4. 数据比对不能替代数据质量

数据比对解决的是：

> 两边数据是否一致？

数据质量解决的是：

> 这一份数据本身是否可信？

例如：

- 迁移前后数据完全一致，但源数据本身就有大量空订单号；
- 目标表和源表行数一致，但金额字段全是负数；
- 两张表比对通过，但数据已经三天没有更新。

这些问题，靠“比对”是发现不了的。

**数据比对看“两边像不像”，数据质量看“自己行不行”。**

## 02 DataY 的数据质量，是什么样子？

DataY 把数据质量拆成两部分：

```text
数据质量
  ├── 质量规则
  └── 质量检核
```

质量规则负责“怎么检查”。

质量检核负责“什么时候检查、检查哪张表、结果怎么保存”。

同时，DataY 把数据质量能力放进了两个地方：

1. **ETL 任务中的数据质量检核组件**：边集成、边检查；
2. **独立的数据质量检核任务**：对一张表做一次完整的质量验收。

## 03 质量规则：把检查口径沉淀下来

DataY 预置了常用的表级规则和字段级规则。

### 表级规则

| 规则 | 说明 |
| --- | --- |
| 表行数下限 | 表里至少要有多少行 |
| 表行数范围 | 表行数是否处于合理区间 |
| 组合字段唯一 | 多个字段的组合是否唯一 |
| 自定义 SQL | 用一条 SQL 返回无效行数 |

### 字段级规则

| 规则 | 说明 |
| --- | --- |
| 字段非空 | 字段是否为 NULL，空白字符串是否算空 |
| 字段唯一 | 字段值是否唯一 |
| 字段值范围 | 数值或日期是否在合理区间 |
| 字段枚举值 | 字段值是否属于允许集合 |
| 字段正则格式 | 字段是否符合指定格式 |
| 字段长度范围 | 字符串长度是否在指定范围 |
| 数据时效 | 时间字段是否足够新 |
| 自定义 SQL | 用一条 SQL 返回无效行数 |

这些规则可以直接使用，也可以复制成自定义规则，调整名称、编码、严重级别和默认参数。

### 两条阈值，决定是否达标

每条规则都可以设置：

- **无效行数 ≤**：允许的最大无效行数；
- **无效比例 ≤**：允许的最大无效比例。

只有两个条件同时满足，规则才算通过。

例如：

```text
订单号非空
无效行数 ≤ 0
无效比例 ≤ 0
```

只要出现一条空订单号，规则就不通过。

再比如：

```text
手机号格式
无效行数 ≤ 100
无效比例 ≤ 0.01
```

允许少量历史脏数据存在，但不能超过总行数的 1%。

### ERROR 和 WARN

规则支持两种严重级别：

- `ERROR`：不达标时，任务失败；
- `WARN`：不达标时，只记录告警，不阻断任务。

这让数据质量可以分级管理：

- 主键、金额、核心枚举，用 ERROR；
- 非核心字段、历史遗留格式，用 WARN。

### 自定义 SQL

有些规则无法用预置模板表达，可以使用自定义 SQL。

要求只有两条：

1. 单条 `SELECT`；
2. 返回 `invalid_rows` 列。

例如：

```sql
SELECT COUNT(*) AS invalid_rows
FROM fact_sales_order
WHERE order_amount < 0
   OR order_amount > 100000000;
```

自定义 SQL 的定位是“兜底”，不是“替代所有规则”。

能用预置规则表达的，优先用预置规则，因为更直观、更容易维护。

## 04 在数据集成中做质量检查

很多数据问题，最好在“写出去之前”就被拦住。

DataY 的 ETL 设计器里新增了 **数据质量检核** 组件。

它可以直接接在数据流中间：

```text
数据源输入 -> 数据质量检核 -> 数据输出
```

也可以接在流程末尾：

```text
数据源输入 -> 数据清洗 -> 数据写入 -> 数据质量检核
```

### 两种检核模式

**FLOW 模式：检查上游数据**

组件接收上游 FlowFile，把数据写入 DuckDB 临时表，所有数据到齐后执行规则。

这种方式不依赖上游是否已经落表，适合：

- 同步前检查源数据；
- 清洗后检查处理结果；
- 写入前做最后一道质量门禁。

**TABLE 模式：检查指定 DuckDB 表**

直接检查指定的 DuckDB 表，适合上游已经通过 `DuckDBWrite`、`JdbcInput`、`StreamSqlUnit` 等组件物化了数据的场景。

### 质量不达标，任务直接失败

当 ERROR 规则不达标时，组件会抛出异常，当前 ETL 任务标记为失败。

也就是说，数据质量不再是一个“事后看报表”的动作，而是任务执行链路中的一道门禁：

```text
数据不合格 -> 任务失败 -> 不继续污染下游
```

WARN 规则只记录告警，不影响任务继续执行。

### 结果依然要留痕

即使任务失败，质量结果也会先写入文件存储：

```text
quality_summary.csv
quality_detail_1_xxx.csv
```

汇总文件记录每条规则的：

- 检核行数；
- 无效行数；
- 无效比例；
- 阈值；
- 状态；
- 说明。

失败规则还会生成抽样明细，方便直接定位问题数据。

结果支持本地文件存储和 MinIO，和 DataY 其他文件类资产保持一致。

## 05 独立的质量检核任务

ETL 里的质量组件解决的是“流程中的质量门禁”。

但很多时候，我们需要的是：

> 对某一张已经存在的表，单独做一次质量验收。

例如：

- 数据迁移完成后，验收目标表；
- 每天对核心事实表做一次巡检；
- 新接入一张业务表，先跑一轮质量检查；
- 数据开发提交模型前，先做一次质量自测。

DataY 的 **质量检核任务** 就是为此设计的。

创建任务时只需要：

1. 选择数据源、Schema、表；
2. 可选填写过滤条件；
3. 从规则库选择规则；
4. 绑定字段、配置阈值和严重级别；
5. 保存并立即执行。

执行时，DataY 会自动生成一条 ETL 任务：

```text
StreamJdbcInput -> DataQualityCheck
```

也就是说，独立质量任务和在 ETL 里使用质量组件，底层执行的是同一套能力。

### 结果怎么看？

任务列表会展示：

- 最近一次执行状态；
- 整体质量结果：通过 / 告警 / 不通过；
- 规则总数、通过数、告警数、失败数；
- 检核行数；
- 最近执行时间。

结果详情里可以看到每条规则的情况：

```text
规则：订单号非空
无效行数：1 / 10000
状态：失败
说明：无效行数 1，超过阈值 0
```

同时可以下载：

- 汇总文件；
- 失败规则的问题数据抽样明细。

### 一个实际的例子

假设我们有一张销售事实表 `fact_sales_order`，配置三条规则：

```text
1. 销售事实表非空：ROW_COUNT_MIN >= 1
2. 订单号非空：NOT_NULL(order_id)
3. 销售金额合法：RANGE(order_amount >= 0)
```

执行结果可能是：

```text
整体结果：不通过
规则总数：3
通过：2
失败：1
失败规则：销售金额合法
```

点开规则明细，可以直接看到无效行数和问题数据抽样。

这就是从“凭感觉”到“有证据”的变化。

## 06 两种方式，怎么选？

| 场景 | 推荐方式 |
| --- | --- |
| 数据同步、清洗、写入过程中的质量门禁 | ETL 数据质量检核组件 |
| 对一张已存在的表做验收或巡检 | 独立质量检核任务 |
| 质量不达标必须阻断下游 | ETL 质量组件 + ERROR 规则 |
| 只记录问题、不阻断流程 | WARN 规则 |
| 需要定时执行质量检查 | 在 ETL 任务中编排质量组件并使用现有调度能力 |
| 临时排查某张表 | 质量检核任务，立即执行 |

可以简单记成：

- **边跑边查**：用 ETL 质量组件；
- **停下来专门查**：用质量检核任务。

## 07 数据质量，不应该是一次性的运动

很多团队做数据质量，习惯搞一次“专项治理”：

- 拉一批人；
- 写一批 SQL；
- 查出一批问题；
- 修完，结束。

过几个月，问题又回来了。

真正有效的数据质量，应该具备三个特征：

1. **规则化**：检查口径固化成规则，而不是散落在个人手里；
2. **可执行**：规则能跟着任务自动跑，而不是靠人记得；
3. **可追溯**：每次检查的结果、失败原因、问题数据都能留下来。

DataY 的数据质量能力，就是围绕这三点设计的：

- 用规则库沉淀检查口径；
- 用 ETL 组件和质量任务自动执行；
- 用任务实例和结果文件保留证据。

DataY 快速入门应用中已经预置了数据质量演示资产：

- **数据质量检核任务**：对 `fact_sales_order` 执行行数、订单号非空、销售金额范围检查；

从“任务成功”到“数据可信”，中间差的不是一条 SQL，而是一套持续运行的数据质量机制。

DataY 想做的，就是把这件事变简单。

## 关于 DataY

DataY 是一套**轻量级数据平台**。

它的目标不是把 Hadoop、Spark、Flink 那一整套重型组件再拼一遍，而是用尽可能简单的技术栈，把数据团队最常用的能力做成一个可以直接运行的整体：

- **数据集成**：支持 MySQL、PostgreSQL、Oracle、SQL Server、DuckDB、Doris、ClickHouse 等二十余种数据源，支持全量、增量、CDC 实时同步；
- **可视化 ETL**：拖拽画布编排输入、清洗、关联、转换、输出，也支持 JSON 任务定义和代码组件；
- **任务调度**：Cron 定时调度、DAG 任务编排、失败重试、实例状态与日志；
- **维度建模与指标管理**：星型 / 雪花模型、维度与事实表、原子指标和衍生指标；
- **数据比对**：跨库、跨表比较记录数和明细差异；
- **数据质量**：质量规则管理、质量检核任务、ETL 流程中的质量门禁；
- **分析与 AI**：SQL 分析数据集、分析看板、智能问数、ETL AI 设计助手。

DataY 的一个典型特点是“轻”：

- 一个 JAR 就能启动；
- 2 核 4G 的机器就能跑通从数据接入到分析看板的完整链路；
- 不依赖 Hadoop、Spark 等外部大数据集群；
- 可以使用内嵌 DuckDB 作为分析引擎，也可以连接 Doris、ClickHouse 等外部引擎。

用一句话概括：

> **DataY = 数据集成 + 任务调度 + 维度建模 + 数据质量 + 数据分析，一体化交付。**

而数据质量，是这套一体化能力中经常被忽略、但越来越重要的一环。
