# 当实时数据流遇上大模型：让业务"边发生、边响应"

> 数据管道跑得再快，也只是把数据搬进数仓、等下一次跑批。
> 但有些事，等不起——一条弹幕、一条差评、一句投诉，必须在发生的那一刻就被读懂、被判级、被响应。
>
> 这篇文章讲清楚一件事：**把大模型做成实时数据流里的一个算子，业务响应就能从"明天看报表"变成"当场就处理"。**

---

## 一、一个"慢半拍"的现实

先看两个我们都熟悉的画面。

**画面 A：直播间运营**
某品牌做了一场大促直播，弹幕每秒涌进来几百条。运营主管盯着屏幕，能看到的只有滚动的文字流。他心里最想知道的几件事——"谁在问价格、谁在犹豫、谁在骂、有没有人发广告"——**没有任何一个系统能实时告诉他。**

等直播结束，数据团队把弹幕导出来跑一遍分析，第二天出个复盘 PPT：昨晚有 320 条高意向询问，其中 47 条转化了。问题是，**直播已经结束了，那张优惠券现在发给谁？**

**画面 B：客服工单**
一位用户连续发来三条消息，情绪越来越激动。客服系统只按"先来后到"排队，主管看不到"这条正在升级的投诉"。等系统报警、等人工发现，用户已经把差评发到社交平台了。

这两个画面的共同点是：

> **数据不是没有，而是"读不懂 + 来不及"。**

传统的实时数据管道能解决"搬得快"：Kafka 进来、CDC 捕获、秒级同步进数仓。但它搬的是 `user_id`、`msg_id`、`content`——它对"这句话到底在表达什么"一无所知。

而 **"读懂语义"这件事，恰恰是大模型的主场。**

于是问题就变成了：**怎么把"读得懂"和"搬得快"缝在一起，不缝出一个外挂服务，而是缝成一条真正的实时流水线？**

---

## 二、先说清楚：为什么"流"和"模型"不能各自为战

遇到上面这种需求，很多团队的第一反应是搭一个独立架构：

```
业务库 / Kafka  ──导出──▶  独立的 AI 服务  ──结果──▶  再导回业务库
```

也就是：数据从流里捞出来，落个临时表，起一个 AI 服务读表、调模型、写回结果。

**这个架构在真实生产里几乎一定会失控**，原因和上一代"ETL + 定时脚本"一模一样：

- 多了一套服务要部署、要监控、要扩缩容、要处理它自己的故障；
- 链路断成两截：流的进度和 AI 的进度对不上，数据卡在中间成了"半成品"；
- 失败重试、幂等、背压、限流，全部要**为 AI 服务重新实现一遍**；
- 最要命的是：**延迟被叠加**。消息先攒批、再落表、AI 服务再轮询，等一圈下来，最佳响应窗口早就过去了。

正确的做法只有一句话：

> **把大模型做成实时数据流里的一个"转换节点"，和过滤、Join、SQL 算子同级。**

它不是"数据平台旁边的一个 AI 服务"，而是"数据流中间的一个处理步骤"。数据流进来，经过这个节点，就带上了模型的判断结果，然后继续往下走——**一条链路、一份状态、一个延迟**。

## 三、这套流水线长什么样

用刚才的直播间场景，画一条完整的实时响应链路：

```
       直播间弹幕 / 客服会话 / 商品评论（实时产生）
                      │
                      ▼   Kafka 消费 / CDC 捕获（秒级入流）
        ┌──────────────────────────────────────────┐
        │            实时处理流水线                   │
        │                                          │
        │  原始消息 ──▶ 【大模型算子】                │  ← 给定输出 Schema
        │                 │ 逐条调用，读语义           │     输出结构化 JSON
        │                 ▼                        │
        │          intent / urgency / sentiment    │
        │                 │                        │
        │                 ▼                        │
        │            【属性路由】 按业务规则分叉        │
        └──────────────────────────────────────────┘
             │            │            │
       购买意向        投诉/负面       违规内容
             │            │            │
             ▼            ▼            ▼
         发优惠券      转人工/告警     实时拦截
             │            │            │
             └────────────┴────────────┘
                          │
                          ▼  全量落库（DuckDB / Doris / ES）
                 实时看板 · 分钟级复盘 · 标签沉淀
```

注意这条链路的三个关键点：

1. **入口是"流"**：消息一产生就进管道，不攒批、不等调度；
2. **中间是"模型"**：逐条给出结构化判断，而不是等攒够一批再分析；
3. **出口是"动作"**：命中的分支直接调业务系统——发券、转人工、拦截，**响应发生在业务还在进行的时候**。

这就是"边发生、边响应"。

## 四、用 DataY 把这条链路搭出来

上面这条流水线，在 **DataY** 里是几个算子连起来就能跑的事。逐个说。

### 第 1 步：让数据"实时进来"

DataY 的实时输入组件覆盖了绝大多数入口：

| 入口 | 组件 | 适用 |
| --- | --- | --- |
| 消息队列 | `KafkaConsumer` | 弹幕、评论、日志等高频消息流 |
| 数据库变更 | `MySQLBinlogInput` / `PostgresCDCInput` / `OracleCDCInput` / `MongoCDCInput` | 订单、工单、会话的增删改 |
| HTTP 推送 | `HttpListener` | 业务方直接 POST 上来的事件 |

以直播间为例，弹幕进 Kafka 的 `live_danmaku` topic，管道用 `KafkaConsumer` 消费，`batchSize` 控制一次处理的条数，`autoOffsetReset`、`startTimestamp` 控制从哪开始——**消息一到就往下游送，不用等整点调度。**

### 第 2 步：插入"大模型"算子，逐条读语义

这是整条链路的核心。DataY 提供 **`LlmComponent`（画布上叫「大模型」）**，它兼容 OpenAI Chat Completions 协议——DeepSeek、通义千问、vLLM、Ollama 都能直接接。

它的行为简单到可以一句话说清：

> **输入一行 JSON，调用一次大模型，把模型返回的 JSON 字段合并进这一行。**

配置只写两个东西——**系统提示词**（定义角色和输出 Schema）和**用户输入**（用动态参数引用当前行字段）：

**系统提示词：**

```text
你是直播间的实时运营助手。请阅读一条弹幕/评论，输出一个 JSON 对象，不要任何解释。字段：
intent（意图，取值：购买意向/咨询/吐槽/投诉/违规/无关）、
urgency（紧急度，0-100 整数）、
sentiment（情感：正面/中性/负面）、
product（涉及的商品，没有则留空）、
summary（不超过 25 字的一句话摘要）、
action（建议动作：发券/转人工/拦截/忽略）。
```

**用户输入：**

```text
观众：${nickname}；弹幕原文：${content}
```

`${...}` 是 DataY 的动态参数语法，按当前行字段取值；还支持 `${attr:属性名}` 取上游属性、`#{NOW - 1d, yyyy-MM-dd}` 这类内置参数。

模型返回 JSON 后，字段被自动展开到当前行。于是一条弹幕从：

```json
{ "user_id": "U8823", "content": "这个价格到底多少钱？能便宜点吗，我马上拍" }
```

变成：

```json
{
  "user_id": "U8823",
  "content": "这个价格到底多少钱？能便宜点吗，我马上拍",
  "intent": "购买意向",
  "urgency": 85,
  "sentiment": "正面",
  "product": "空气炸锅",
  "summary": "询价且明确有下单意愿",
  "action": "发券"
}
```

**从这一行开始，弹幕就从"文本"变成了"可编程的结构化信号"。**

> 一个工程细节：如果模型返回的不是合法 JSON，组件不会让整条管道炸掉——它会退化成文本，写进 `llm_result` 字段继续往下传。**脏输出不丢数据。**

### 第 3 步：属性路由，按业务规则分叉

有了 `intent`、`urgency` 这些字段，接下来就是"这类消息该走哪条路"。

DataY 的 **`RouteOnAttribute`（属性路由）** 就是干这个的：在**连线上写标签**，数据自己找路。用"按数据项"模式，指定 `dataField = intent`，就能把混合的一批弹幕自动拆到不同分支：

```
                          ┌── 购买意向 ──▶ 发优惠券
   弹幕 ──▶ 【大模型】 ──▶ 【属性路由】├── 投诉   ──▶ 转人工 + 告警
                          ├── 违规   ──▶ 内容安全拦截
                          └── other  ──▶ 兜底分支
```

**未匹配的自动走 `other` 兜底**——这是路由最值钱的一个设计：以后业务新增任何一类意图，数据都不会无声无息地丢掉，而是全部被 `other` 接住，可查、可告警。

### 第 4 步：实时响应，动作直接回调业务系统

分好路，就要"动手"了。DataY 的 **`HttpInvoke`（HTTP 调用）** 支持 GET/POST，Body 里同样能用动态参数引用当前行字段，把模型的判断结果回传给业务系统：

- 命中「购买意向」→ 调营销系统接口，给用户发优惠券、推私信；
- 命中「投诉」→ 调客服系统，把这通会话**打上高优先级**并通知主管；
- 命中「违规」→ 调内容安全接口，实时拦截；
- 全量数据再广播一路落 `DuckDBWrite` / `DorisStreamLoad` / `ElasticsearchOutput`，进实时看板。

**这就是"实时响应"的闭环：消息在流动的过程中被理解、被分流、被处理，全程不需要人工旁路等待。**

## 五、"实时"不等于"无脑逐条调用"，这些工程问题必须回答

把大模型放进实时流，难点从来不是"接得上"，而是"跑得稳、算得清、接得住流量"。几个绕不开的问题：

**① 延迟到底是多少？**

单条消息的端到端延迟 ≈ 排队时间 + 模型调用时间。DataY 的实测中，单次大模型调用在 **0.5~1.2 秒**量级。对"直播运营、客服派单、舆情预警"这类场景，**秒级响应已经足够改变结果**——它远快于"等跑批、等看板"。

如果业务要求更苛刻（比如风控毫秒级拦截），正确做法不是让大模型硬扛，而是：**规则先行、模型兜底**。用 `StreamSqlUnit` 或 `RouteOnAttribute` 先把明显规则的事在毫秒级处理掉，只有"需要理解语义"的那一小部分才送进模型算子——**让大模型只处理它真正擅长的那部分数据。**

**② 流量一大，逐条调用扛得住吗？**

现实里高频流每秒几千条，逐条调用当然不现实。但业务需求本身也是分层的：

- **上游先收敛**：广告、灌水、"666"这类无信息弹幕，可以用关键词或规则提前过滤，不进模型；
- **增量而非全量**：CDC 只处理变更数据，历史数据一次性回补；
- **任务级并行**：按分区、按直播间、按时间段拆成多个任务实例并发跑。

**③ 失败、重试、幂等怎么办？**

`LlmComponent` 内置了 `retryCount`（含首次）和 `retryIntervalMillis`，超时等可重试错误自动重试并记录完整异常链；任务被取消或超时会直接中断，不会无限重试拖住整条流。

幂等的正确姿势是：**按业务主键（`msg_id` / `user_id + 时间戳`）在落库和回调侧做去重**，而不是依赖"每次模型结果完全一致"。

**④ 成本是多少？**

这可能是最不需要担心的一项。实际使用中，单条短提示词的 `promptTokens` 在百级、`completionTokens` 在几十级。即使把完整的标签字典和 Schema 写进系统提示词，按主流国产模型（`deepseek-chat` 一档）的单价量级折算，**10 万条消息的成本也只有几十元**——相比"人工实时盯屏 + 事后打标签"的人力，这个量级可以直接立项。

> 真实价格以模型厂商当期定价为准（含缓存命中、错峰优惠等），这里只做量级判断。

**⑤ 提示词散落各处，怎么治理？**

- **Schema 收敛**：`intent` 用枚举值，别让模型自由发挥；
- **低温度**：`temperature` 保持低值（如 0.1~0.2），减少同类消息判断抖动；
- **人工抽检**：定期抽样复核，把错判样本补进提示词——**改一行提示词当天生效**，这是相对"训练定制模型"最大的工程优势；
- **统一维护**：同一份 Schema 和提示词模板在平台里集中管理，避免口径分叉。

## 六、这条路走通之后，变化是什么

回到开头的两个画面。

**直播间**：高意向弹幕出现的**同一秒**，优惠券已经发到了用户私信；投诉弹幕出现的**当下**，客服主管的企微已经响了；违规内容在**展示之前**就被拦截。直播还在进行，运营已经在实时调整话术和库存。

**客服**：情绪升级的会话被自动打上高优先级，不再排在大堆普通工单后面；重复的咨询类问题在工作时间内自动应答；负面舆情的苗头在**扩散之前**就被识别、被上报。

技术上的本质变化只有一句话：

> **非结构化数据第一次可以"不经过人工、不经过定制模型"，实时地变成数仓里可聚合、可路由、可编程的字段。**

而它进入数据链路最自然的方式，不是作为一个外部的 AI 服务，而是作为**数据流里的一个转换节点**——和过滤、Join、SQL 算子站在一起，共用同一套调度、重试、监控和状态。

## 七、DataY 是什么

上面这条实时响应流水线，跑在 **DataY** 上。它是一个**开源、轻量的一体化数据平台**：

> 一个 JAR、内嵌 DuckDB，**2 核 4G** 就能跑通「数据集成 → 数据建模 → 数据开发 → 任务调度 → 数据应用」的完整链路。

它由「一个引擎 + 一个平台」组成：

| 模块 | 定位 | 说明 |
| --- | --- | --- |
| **DataY Core** | 数据集成引擎 | 轻量、可嵌入、流批一体；JSON 定义任务、自动建表、CDC 实时同步；可脱离 Web 独立运行，或嵌入 Java 应用 |
| **DataY Web** | 可视化数据平台 | 拖拽式任务设计、Quartz 调度、维度建模、指标管理、智能问数 |

**五大能力：**

- 🔌 **数据集成**：MySQL / PostgreSQL / Oracle / SQL Server / Doris / ClickHouse / DuckDB 等十余种数据源，支持 MySQL Binlog、PostgreSQL WAL、Oracle LogMiner、MongoDB Change Streams CDC 实时同步，Kafka 消费，自动建表与 DDL 转换；
- 📐 **维度建模**：星型 / 雪花模型，普通维度、层级维度、时间维度（自动预置日期数据），事实表外键一键关联；
- ⏰ **任务调度**：Quartz Cron 精确到秒，DAG 拓扑编排，父子任务依赖，失败重试，master / worker 可分离部署；
- 🚀 **高性能数仓**：内嵌 DuckDB（列存 + 向量化），支持 DuckLake（Iceberg 格式）构建数据湖，需要时外挂 Doris / ClickHouse；
- 🤖 **智能问数**：自然语言 → 指标 → 维度 → 时间过滤 → 取数，一句话拿报表，指标口径统一维护。

**以及让 AI 长在链路上的 AI 原生底座：**

- **管道内的 `LlmComponent`**：逐行调用大模型，把非结构化文本变成结构化字段；
- **面向 Agent 的 MCP Harness**：通过 `/mcp/datay` 把数据源、ETL 任务、数据模型的管理动作和指标问数能力暴露给 Claude Desktop / Cursor 等客户端，Agent 可自行完成「建数据源 → 建 ETL 任务并试跑 → 上线调度 → 建模落表 → 问指标」，复用平台既有的鉴权与租户隔离，写操作可一键降级为只读。

## 八、写在最后

过去几年，实时数据流解决的是"搬运"问题：让数据"更快地到达数仓"。
大模型解决的是"理解"问题：让机器"看懂"文字背后的意图。

但真正决定业务结果的，不是其中任何一件，而是**两者缝在一起的那条链路**：

> **数据在流动的过程中就被理解，理解的结果立刻变成动作。**
