# 一个编排，装下另一条流水线：DataY 任务编排支持嵌套了

> 把复杂流程拆成多个可复用的子编排；
> 父编排负责顺序，子编排负责边界；
> 一次引用，多层展开，执行与日志依然完整可追踪。

---

## 01 一张 DAG，画到最后为什么越来越难维护？

任务编排刚上线时，画布通常很清爽：

```text
同步订单 → 清洗订单 → 生成汇总 → 刷新报表
```

后来业务越来越多，画布开始膨胀：

- 订单、商品、库存、门店，各自都有一条同步链路；
- 每条链路后面都要做清洗、汇总、质量校验；
- 有些流程还要被多个业务场景复用；
- 某一段流程出问题，整张大图都要重新梳理。

最后，一张画布上挤进了几十个节点。

看起来“全都在一起”，实际维护起来却是：

> **牵一发，动全身。**

改一个公共流程，要在一张大图里找半天；
排查一次失败，要沿着密密麻麻的连线往回倒；
想让另一个业务复用同一段流程，只能复制粘贴，然后维护两份。

问题的本质不是 DAG 不够强，而是：

> **所有复杂度都压在了同一层。**

复杂流程需要分层。

就像代码里不会把所有逻辑写进一个函数，任务编排也不应该把所有任务画进一张图。

DataY 这次带来的能力是：

> **任务编排可以嵌套任务编排。**

一个编排里，可以把另一个已经存在的编排当作节点拖进来。

---

## 02 嵌套编排是什么？

先用一句话说清楚：

> **编排节点不再只能是 ETL、SQL、Shell，也可以是一个完整的任务编排。**

比如原来一张大图是这样：

```text
同步日期维度
同步商品维度
同步门店维度
同步订单事实
清洗订单明细
生成销售汇总
生成品类排行
质量校验
...
```

现在可以拆成：

```text
主编排
  ├─ 维度同步子编排
  ├─ 事实同步子编排
  ├─ 数据汇总子编排
  └─ 质量校验子编排
```

主编排只关心“先做哪一段、再做哪一段”；
每个子编排内部，继续用 DAG 描述自己的任务顺序。

画布从“几十个节点”，变成了“几个清晰的阶段”。

### 它不是复制，而是引用

这一点非常重要。

把编排 A 拖进编排 B 时，B 里保存的是 A 的任务 ID，而不是 A 的一份副本。

这意味着：

- A 里的任务调整后，B 下次运行会自动使用最新定义；
- 不需要维护两份相同的流程；
- 子编排仍然可以独立上线、独立执行；
- 父编排和子编排可以分别由不同同学维护。

和代码里的“函数调用”很像：

> **子编排是一段被复用的流程，而不是一段被复制出来的文本。**

---

## 03 怎么用？三步搭出嵌套编排

### 第一步：先准备好子编排

在「数据开发 → 任务编排」里，先把可以独立成段的流程建好。

例如：

- 维度同步编排；
- 事实同步编排；
- 汇总编排；
- 质量校验编排。

每个子编排本身就是一个完整的 DAG，可以单独执行、单独查看日志。

### 第二步：在父编排里拖入子编排

新建或打开父编排，左侧候选任务列表里会多出一个「任务编排」分组。

把需要的子编排拖到画布上即可。

子编排节点会显示为：

```text
DAG · 子编排
```

和普通任务节点区分开。

当前正在编辑的编排不会出现在自己的候选列表里，避免直接把自己拖进自己。

双击子编排节点，可以查看它的详情；详情弹窗里提供「打开子编排设计」，会在新标签页打开子编排画布，不会丢失当前父编排的编辑状态。

### 第三步：像普通节点一样连线

子编排节点和普通任务节点一样，可以参与依赖连线：

```text
维度同步子编排
      ↓
事实同步子编排
      ↓
数据汇总子编排
      ↓
质量校验子编排
```

连线表达的含义不变：

> **A → B，表示 A 成功执行完之后，才执行 B。**

保存后，父编排默认仍然是离线状态。

建议先点一次「立即执行」，确认每一段子编排都能正常跑完，再配置 Cron 上线。

## 04 运行时，嵌套编排是怎么展开的？

画布上看到的是“一个节点里套着另一个编排”，执行时并不是黑盒。

当父编排被触发时，DataY 会递归展开整棵编排树：

```text
父编排实例
  ├─ 子编排实例
  │    ├─ 子任务实例
  │    ├─ 子任务实例
  │    └─ 子任务实例
  ├─ 普通任务实例
  └─ 另一个子编排实例
       └─ ...
```

每一层都会生成真实的实例记录，并保留父子关系。

也就是说：

- 父编排有自己的实例状态；
- 子编排有自己的实例状态；
- 子编排里的每个任务也有自己的实例状态；
- 每一层都可以单独定位开始时间、结束时间、执行节点和日志。

子编排内部仍然按照自己的 DAG 拓扑顺序执行。

父编排只负责在正确的时间点启动这个子编排，并等待它完成。

### 多层嵌套也支持

一个子编排里还可以继续嵌套另一个子编排。

DataY 当前允许最多 **10 层**嵌套。

但建议不要为了嵌套而嵌套。

大多数业务拆到 2～3 层已经足够清晰：

```text
业务主流程
  └─ 领域子流程
       └─ 公共任务组
```

层级越深，阅读成本越高。

---

## 05 循环嵌套，会在保存时被拦住

嵌套编排最怕的一件事，是“绕回去”：

```text
A 嵌套 B
B 嵌套 C
C 又嵌套 A
```

运行时就会无限展开。

DataY 在保存时会递归检查嵌套关系，并阻止以下情况：

- 编排直接嵌套自己；
- 编排间接嵌套自己；
- 嵌套层级超过上限。

错误提示会带上完整路径，例如：

```text
任务编排存在循环嵌套: A -> B -> A
```

设计器里也会过滤当前编排，避免直接把自己拖进画布。

运行时还有一层兜底校验，即使数据被其他方式改坏，也不会无限递归。

## 06 失败、取消与日志，嵌套后还能看清楚吗？

这是嵌套编排最重要的部分。

如果只是“能拖进去”，但运行起来看不见、失败了查不到，那这个能力没有意义。

### 子编排失败，父编排会失败

子编排内部任意一个任务失败，子编排实例会失败，父编排也会收到失败结果。

父编排中尚未执行的后续节点，会被标记为 `INTERRUPTED`。

### 取消会向下传递

父编排被停止或超时时，会取消当前正在执行的子编排。

子编排会继续取消它内部正在执行的任务。

尚未执行的嵌套子任务也会被递归标记为 `INTERRUPTED`，不会留下一批永远停在 `APPENDING` 的“孤儿实例”。

### 日志按层级展开

打开父编排实例的日志，会看到完整的嵌套任务列表，并按层级缩进：

```text
父编排
  ├─ 维度同步子编排
  │    ├─ 同步日期维度
  │    ├─ 同步商品维度
  │    └─ 同步门店维度
  ├─ 事实同步子编排
  │    └─ 同步销售订单事实
  └─ 数据汇总子编排
       ├─ 清洗订单明细
       └─ 生成销售汇总
```

每个节点仍然可以单独展开查看日志。

刷新、下载日志时，层级顺序也会保留。

这解决的是一线排查时最实际的问题：

> **不用先猜问题在哪个子编排，再一层层点进去找。**

## 07 什么场景适合嵌套编排？

### 场景一：把一条超长流水线拆成阶段

```text
主编排
  ├─ ODS 同步子编排
  ├─ DWD 清洗子编排
  ├─ DWS 汇总子编排
  └─ ADS 输出子编排
```

每一层只关注自己的边界，主编排关注阶段顺序。

### 场景二：公共流程被多个业务复用

例如“同步 → 清洗 → 质量校验”是一段公共流程。

销售日更编排可以引用它；
库存日更编排也可以引用它。

修改公共流程，只需要改子编排本身。

### 场景三：按团队或业务域拆分维护

- 数据接入团队维护同步子编排；
- 数仓团队维护清洗和汇总子编排；
- 质量团队维护校验子编排。

父编排只负责把大家的工作串起来，不需要所有人都挤在同一张画布上改。

### 场景四：复杂流程需要分级发布

子编排可以先独立上线、独立验证。

确认稳定后，再被父编排引用。

## 08 也要说清楚边界

嵌套编排不是“画得越深越高级”。

当前版本有几个明确边界：

- **最多 10 层嵌套**，超过会在保存或运行时被阻止；
- **引用而不是复制**，子编排修改后，父编排下次执行会使用最新定义；
- **同一个编排在单张画布中只添加一次**，避免节点 ID 冲突；
- **子编排仍然可以独立调度**，父编排引用它，不改变它自己的 Cron 和上下线状态；
- **当前 DAG 子任务仍按拓扑序串行推进**，嵌套不会自动把不同分支拆到多个 Worker 并行执行；
- **动态条件分支、循环子流程**仍不在当前能力范围内。

我们更愿意把这些边界写清楚，而不是把“支持嵌套”说成“什么流程都能画”。

## 09 五个实践建议

### 1. 一个子编排，只承担一个清晰职责

推荐按“阶段”或“业务域”拆分：

```text
维度同步子编排
事实同步子编排
汇总子编排
质量校验子编排
```

不要把一个子编排做成“什么都干”的杂物间。

### 2. 子编排命名带上前缀

例如：

```text
子编排｜维度同步
子编排｜事实同步
子编排｜数据汇总
```

拖到父画布后，一眼就能看出这是编排节点，而不是普通任务。

### 3. 控制嵌套深度

2～3 层通常已经足够。

如果发现需要嵌套五六层，先问一句：

> 是不是流程边界没有设计好？

### 4. 子编排同样要保证幂等

父编排重试时，会整体重跑子编排。

子编排里的任务如果重复写入会产生重复数据，嵌套只会把这个问题放大。

### 5. 先用“立即执行”验证整棵树

嵌套后，不要只看子编排单独跑成功。

还要验证：

- 父编排是否按正确顺序启动子编排；
- 子编排失败后，父编排后续节点是否被中断；
- 停止父编排时，子编排内部任务是否被取消；
- 日志层级是否完整。

---

## 10 写在最后

任务编排的价值，不是把所有任务塞进一张图。

而是让复杂流程变得：

- **可拆分**：一段流程一个边界；
- **可复用**：公共流程只维护一份；
- **可追踪**：每一层执行都有实例和日志；
- **可收场**：失败、超时、取消都能向下传递。

嵌套编排带来的，不只是画布上多了一种节点。

它让任务编排从“一张图”，变成了“一组可以组合的流程积木”。

**复杂流程，不应该靠一张越来越大的图来承载。**

**该分层的时候，就让它分层。**
