# 当大模型嵌入数据管道：不止聊天，如何让非结构化数据真正进入数仓

> 以电商用户反馈 VOC 流水线为例：把大模型从一个"聊天窗口"，改造成流水线里的一个转换节点。

---

## 一、一个每周都在发生的场景

周三下午，产品经理又来找数据同学：

> "帮我看看，最近差评里到底在骂什么？包装破损有多少？功能故障有多少？客服态度问题的占比是不是涨了？"

数据同学打开数仓看了一眼，只能说：**表里只有评分和文本，没有"问题类型"这个字段。**

于是接下来的一周是这样的：

1. 运营从评价、工单、售后备注里导出几万条文本；
2. 在 Excel 里按关键字（"破损""坏了""售后""垃圾"）粗筛；
3. 人工抽样打标签，整理出几百条；
4. 做一份 PPT，结论是"包装问题比较多"，再附上几张用户截图。

等这一轮做完，往往已经过去一周多，**热点早就换了一轮**。下一次要换个口径再看，还得重新导、重新筛、重新打标签。

这不是数据团队不努力，而是**数据管道天生只认结构化数据**：它能搬运 `order_id`、`amount`、`created_at`，却对"这个快递盒被压瘪了，耳机盒上有压痕"这句话一无所知。

要统计"哪些是包装破损、哪些是功能故障、哪些是客服态度问题"，就必须先做一件事：**把一句话，变成几个字段。**

---

## 二、卡点：用户之声（VOC）永远停在数仓门外

电商平台每天产生的文本是海量的：

- 商品评价
- 客服聊天工单
- 退换货备注
- 直播间弹幕
- 售后投诉

这些数据其实**已经进了数据管道**——评价和会话通过 Kafka 实时同步，落进了 ODS 层。但它们的归宿通常只有一个：**躺在那里，没人能聚合它。**

历史上，想让它"可分析"，只有两条路，而且都不好走：

| 阶段 | 做法 | 代价 |
| --- | --- | --- |
| ① 关键字规则 | `LIKE '%破损%'`、`LIKE '%坏了%'` | 只能做简单过滤。"东西收到就是坏的"命中不了；"包装没破损，但客服没人接"会被误判。同义、反讽、多问题混写全部失效 |
| ② 定制 NLP 模型 | 标注样本 → 训练分类模型 → 上线 | 要标注、要调参、要维护。**业务标签一变（比如新增"直播承诺不符"），整套流程重来**，周期以周甚至月计 |
| ③ 大模型抽取 | 给定输出 Schema，直接抽取结构化字段 | 不用标注、不用训练；标签调整 = 改一行提示词，当天生效 |

前两条路的共同问题是：**把"业务标签的定义权"交给了工程流程。** 业务想多看一个维度，就得排队等一个模型迭代周期。

而三个阶段的成本结构也完全不同：

- 规则：便宜，但覆盖率低；
- 定制模型：固定成本极高（标注 + 训练 + 迭代），边际成本低；
- 大模型：固定成本几乎为零，边际成本是 token 费。

对绝大多数"标签还在变、口径还没稳定"的业务场景来说，**大模型是唯一能跟上业务节奏的方案。**

---

## 三、关键一步：不是让大模型当后台服务，而是让它进管道

很多团队的第一反应是：起一个独立的 AI 服务，数据从数仓导出 → 调 API → 结果再导回数仓。

**这个架构在真实生产里会迅速失控：**

- 多一套服务要部署、要监控、要扩缩容；
- 数据链路断成两截：管道跑完了，AI 服务还没跑完，数仓里的数据是"半成品"；
- 失败重试、增量、幂等、背压，全部要重新实现一遍；
- 数仓里的指标口径和 AI 服务里的口径逐渐分叉。

正确的做法是：**把大模型做成数据管道里的一个转换节点（Transform Operator），和 Join、Filter、SQL 算子同级。**

也就是说，管道长这样：

```
评价 / 客服会话 / 售后备注 / 直播弹幕
              │
              ▼  Kafka / CDC 实时同步（数据集成）
        ┌───────────────────────────────┐
        │      VOC 流水线（流批一体）      │
        │                               │
        │  ODS 原文 ──▶ 【大模型节点】    │  ← 给定输出 Schema
        │                 │             │     输出结构化 JSON
        │                 ▼             │
        │            结构化字段 ──▶ 数仓事实表
        └───────────────────────────────┘
              │
              ▼
    VOC 分析宽表 ──▶ BI 看板 / 投诉趋势 / 售后热点
              │
              ▼
        标签数据沉淀，反哺产品与供应链复盘
```

### 为什么"在管道内"这么重要

1. **一条链路、一份状态**：增量、重试、调度、监控全部复用管道既有能力，不需要为 AI 单独造一套；
2. **Schema 是一等公民**：模型输出被约束成明确字段，落表、建模、指标定义都在同一套体系里；
3. **流批一体**：同一份任务定义，历史数据用批跑回补，新数据用流实时打标；
4. **失败可控**：节点失败 = 任务失败，可以重试、可以告警、可以补数，和普通 ETL 没有区别。

### 输出 Schema 长什么样

给模型的"契约"通常是这样的（这就是我们下面要用的真实配置）：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `category` | 问题大类 | 包装物流 / 商品质量 / 功能故障 / 描述不符 / 客服服务 / 其他 |
| `sub_tag` | 细分故障标签 | 包装破损、涂层脱落、无法开机、尺码偏小、响应不及时 |
| `sentiment` | 情感倾向 | 负面 / 中性 / 正面 |
| `negative_score` | 负面程度 | 0 ~ 100 整数 |
| `summary` | 问题摘要 | "快递盒瘪损，耳机盒有压痕" |

模型返回 JSON，管道把它**按字段展开到当前行**，后面就是纯粹的、可 SQL、可建模、可聚合的结构化数据了。

## 四、动手：用 DataY 的大模型组件搭这条流水线

DataY 提供的大模型组件叫 **`LlmComponent`（画布上叫「大模型」）**。它的定位非常明确：

> 一个按行调用大模型的数据处理算子，输入 JSON 行，输出 JSON 行。

核心行为只有两条：

- **按行处理**：每条用户反馈独立构造一次请求，互不干扰；
- **JSON 扩充、文本兜底**：模型返回的是 JSON 对象，就把字段合并进当前行；返回的是普通文本，就写进 `llm_result` 字段继续往下传，不会让脏输出炸掉整条流水线。

下面是完整的搭建过程（下面的数字和输出，都是我刚刚在本地真实跑出来的一整条流水线的结果）。

### 第 1 步：配置大模型服务（一次配置，全局可用）

在 **系统设置 → 服务配置 · 大模型** 里填一次：API 地址、API Key、模型、温度、超时（公开的 OneAPI / vLLM / Ollama 等只要兼容 OpenAI Chat Completions 协议，都能直接接）。

也可以走系统级配置（环境变量 / 配置文件 `datay.ai.*`）：

### 第 2 步：接入业务数据源

评价、客服工单、退换货备注、直播弹幕，通过 **数据集成** 进入管道：

- 批量：`StreamJdbcInput`  一类组件直连业务库；
- 实时：`MySQLBinlogInput` / `PostgresCDCInput` 捕获业务库变更，或 `KafkaConsumer` 直接消费评价 / 弹幕 Topic。

为了便于复现，我用 DuckDB 造了一张和线上同构的 ODS 表 `ods_voc_feedback`，30 条数据，覆盖 评价 / 客服工单 / 客服会话 / 售后备注 / 直播弹幕 五种渠道：

```
feedback_id | product_id | product_name | channel | feedback_text | create_time
F10001      | P1001      | 无线蓝牙耳机  | 评价    | 拆开快递盒，包装已经瘪了一块，里面的耳机盒有压痕…… | 2024-10-01 09:12:00
F10003      | P1001      | 无线蓝牙耳机  | 客服工单 | 用户来电说左耳没有声音，重启、重置都试过……      | 2024-10-02 10:41:00
```

### 第 3 步：插入「大模型」节点，写清楚 Schema

在画布上把「大模型」组件拖到中间，**只需要配置两个输入框**：

**系统提示词**（定义角色和输出 Schema）：

```text
你是电商平台的用户之声（VOC）分析助手。请阅读一条用户反馈文本，输出一个 JSON 对象，
不要输出任何解释。字段定义：
category（问题大类，取值：包装物流/商品质量/功能故障/描述不符/客服服务/其他）、
sub_tag（细分标签，如 包装破损、涂层脱落、无法开机、尺码偏小、响应不及时 等，6 字以内）、
sentiment（情感：负面/中性/正面）、
negative_score（负面程度 0-100 的整数，0 表示无负面）、
summary（不超过 25 字的问题摘要）。
```

**用户输入**（用动态参数引用当前行字段）：

```text
渠道：${channel}；商品：${product_name}；用户反馈原文：${feedback_text}
```

`${...}` 是 DataY 的动态参数语法，按当前行取值；也支持 `${attr:属性名}` 取上游属性、`#{...}` 引用内置参数（如 `#{UUID}`、`#{NOW - 1d, yyyy-MM-dd}`）。

### 第 4 步：连到数仓，落事实表

下游接 `DuckDBWrite`（或 `StreamJdbcOutput` / `DuckLakeWrite` / `ModelWrite`），模型产出的新字段会自动进入表结构：

```
feedback_id | product_id | product_name | channel | feedback_text | create_time
            | category | sub_tag | sentiment | negative_score | summary
```

生成的流水线 JSON（这就是画布保存后真正交给引擎执行的东西，可直接给 DataY Core 独立运行）：

```json
{
  "units": [
    { ".id": "voc_input",  ".name": "StreamJdbcInput", "schema": "main", "table": "ods_voc_feedback" },
    { ".id": "voc_llm",    ".name": "LlmComponent",
      "systemPrompt": "你是电商平台的用户之声（VOC）分析助手……",
      "userPrompt": "渠道：${channel}；商品：${product_name}；用户反馈原文：${feedback_text}" },
    { ".id": "voc_output", ".name": "DuckDBWrite", "table": "dwd_voc_tagged", "model": "overwrite" }

  "connections": [
    { "sourceId": "voc_input", "targetId": "voc_llm", "sourcePort": 0 },
    { "sourceId": "voc_llm",   "targetId": "voc_output", "sourcePort": 0 }
  ]

```

### 第 5 步：跑起来，看真实结果

任务执行日志（节选，真实运行输出）：

```text

  userPrompt=渠道：评价；商品：无线蓝牙耳机；用户反馈原文：拆开快递盒，包装已经瘪了一块……
[LlmComponent-voc_llm] 大模型返回：行=1，耗时 1063 ms，promptTokens=177，completionTokens=44，
  内容={"category": "包装物流", "sub_tag": "包装破损", "sentiment": "负面",
        "negative_score": 60, "summary": "快递包装瘪损，耳机盒有压痕"}
...
[StreamJdbcInput-voc_input] 表 ods_voc_feedback 同步完成，共处理 30 条记录
```

**30 条反馈 → 22 条判定为负面，平均负面分 53.8，全链路耗时约 25 秒，全部落表为结构化字段。**

落表之后，直接 SQL 聚合 —— 这就是从"人工打标签"到"随时可查"的变化：

**问题大类分布**

| category | 条数 | 平均负面分 |
| --- | --- | --- |
| 功能故障 | 10 | 75.5 |
| 其他（咨询 / 好评） | 7 | 0.0 |
| 描述不符 | 4 | 72.5 |
| 包装物流 | 4 | 60.0 |
| 客服服务 | 3 | 50.0 |
| 商品质量 | 2 | **90.0** |

**按商品看负面集中度**

| 商品 | 负面条数 | 平均负面分 |
| --- | --- | --- |
| 空气炸锅 | 4 | **90.0** |
| 女士羽绒服 | 4 | 72.5 |
| 无线蓝牙耳机 | 4 | 65.0 |
| 儿童学习桌 | 2 | 80.0 |
| 儿童安全座椅 | 2 | 75.0 |
| 智能手表 | 2 | 70.0 |

**细分标签沉淀**（模型自己归纳出的标签，可直接当标签字典用）

```text
尺码偏小 / 响应不及时 / 单耳无声 / 涂层脱落 / 蓝牙连不上 / 无法开机
颜色不符 / 包装破损 / 升降杆卡死 / 物流太慢 / 无问题 / 价格实惠
```

几个只有真跑一遍才会发现的细节：

1. **它真的读懂了语义**。"拆开快递盒，包装已经瘪了一块，里面的耳机盒有压痕，耳机本身没坏" → `包装物流 / 包装破损`，而不是误判成"商品损坏"；"安装说明书太简单……客服电话打了三次都没人接" → `客服服务 / 响应不及时`，抓的是真正让用户愤怒的那一点；
2. **它区分了强弱**。"插上电完全没反应" 给 90 分，而"包装瘪了一块"只给 60 分 —— 这正是投诉趋势排序需要的信号。空气炸锅 4 条负面、平均 90 分，是这批数据里最该立刻看的产品；
3. **它没有被噪声带偏**。"习惯好评，先给五星，后续有问题再追评" 被正确判为 `中性 / negative_score=0`，没有污染负面池；
4. **一句话里有两个问题，它只给一个主标签**。"杯子挺好，就是物流太慢了……客服还一直让我等" 被判为 `包装物流 / 物流太慢`。如果你想同时统计"客服服务"，就要把 Schema 改成多标签输出（`categories` 数组），而不是指望模型自己拆 —— **Schema 设计决定分析口径**；
5. **同一句重复文本，分数有 ±5 的抖动**（同一商品的两次相同文本，negative_score 分别是 55 和 60）—— 这是必须正视的工程问题，下面单说。

### 第 6 步：下游照常使用

到这里，VOC 就变成了"普通的结构化数据"，下游该怎么做就怎么做：

- 用 `DuckDBSql` / SQL 任务构建 **VOC 分析宽表**：`商品 × 日期 × 问题大类 × 细分标签`，带负面条数、平均负面分；
- 对接 BI 看板：**各商品投诉趋势**、售后热点 TOP N、渠道分布（评价 vs 工单 vs 弹幕）；
- 做维度建模：把 `category` / `sub_tag` 建为普通维度，`create_time` 接时间维度，挂到事实表上；
- 定义指标：`负面反馈数`、`平均负面分`、`客服服务问题占比`，进入统一的指标管理，供 智能问数 / 指标查询面板 使用 —— 业务自己一句话问："上个月空气炸锅的负面反馈有多少条？"
- 标签数据持续沉淀，供给产品、供应链做复盘。

## 五、工程落地必须回答的几个问题

把大模型放进管道，难点从来不是"接得上"，而是"跑得稳、算得清"。这几点在 DataY 里都有对应的设计：

**① 逐行调用，量大了怎么办？**

这是最现实的问题。按上面实测的节奏（单条约 0.5~1.2 秒，串行 30 条约 25 秒），百万级数据串行跑是不现实的。

- 上游先收敛：新增反馈、投诉工单、低分评价优先处理，好评和无关弹幕可以过滤或跳过；
- 增量而非全量：CDC / 增量字段只处理变更数据，历史数据一次性回补；
- 任务级并行：调度侧可以把不同主题、不同时间段拆成多个任务实例并发跑。

**② token 成本到底多少？**

实测单条：`promptTokens≈171`、`completionTokens≈43`。要注意这只是本文这种短提示词的量；生产上系统提示词里会写完整的标签字典和输出 Schema，单条通常按 400 token 量级估算：

> **10 万条反馈 ≈ 4000 万 token**，按当前主流国产模型（`deepseek-chat` 一档）的输入/输出单价量级折算，**成本在几十元级别 —— 单条不到千分之一元**。

相比人工抽样打标签的人力成本，这个量级是可以直接立项的。真实价格以模型厂商当期定价为准（含缓存命中、错峰优惠等策略），这里只做量级判断。

**③ 失败怎么办？**

组件内置了重试：`retryCount`（含首次）、`retryIntervalMillis`，超时等可重试错误会自动重试，并记录完整异常链。任务被取消或调试超时会直接抛「大模型调用被中断」，不会无限重试拖住整个管道。极端情况下模型返回的不是 JSON，就落到 `llm_result` 字段，管道继续走，数据不丢。

**④ 幂等和顺序？**

按行调用，每行独立；同一批数据重跑会得到新结果（分数可能略有变化）。生产上的正确姿势是**按 `feedback_id` 做幂等去重**，并用增量字段控制重复消费，而不是依赖"每次结果完全一致"。

**⑤ 提示词散落在各任务里，怎么治理？**

- 标签体系收敛：`category` 用枚举，`sub_tag` 允许模型归纳再由人工定期归并；
- 输出强度：`temperature` 保持低值（我们用的是 0.1）；
- 抽检兜底：人工定期抽样复核，把错判样本沉淀成提示词的补充说明 —— **改提示词当天生效，这是相对训练模型最大的工程优势**；
- 一致性：同一份 Schema 与提示词模板，在管道里统一维护，避免口径分叉。

**⑥ 还能不能更强？**

`LlmComponent` 的底层是 DataY Core 的共享客户端 `OpenAiCompatibleClient`，与平台 AI 助手同源实现，**支持 function calling**，并预留了 `resolveTools()` 扩展点。也就是说，这个节点未来可以不只是"分类器"，还能接工具、做多轮推理，变成管道内的一个 Agent 算子。

**五大能力：**

- 🔌 **数据集成**：MySQL / PostgreSQL / Oracle / SQL Server / Doris / ClickHouse / DuckDB 等十余种数据源，支持 MySQL Binlog、PostgreSQL WAL CDC 实时同步，Kafka 消费，自动建表与 DDL 转换；
- 📐 **维度建模**：星型 / 雪花模型，普通维度、层级维度（自动生成 `levelN_id/name`）、时间维度（年/季/月/日 + 预置日期数据），事实表外键一键关联；
- ⏰ **任务调度**：Quartz Cron 精确到秒，DAG 拓扑编排，父子任务依赖，失败重试，master / worker 可分离部署；
- 🚀 **高性能数仓**：内嵌 DuckDB（列存 + 向量化），支持 DuckLake（Iceberg 格式）构建数据湖，需要时外挂 Doris / ClickHouse；
- 🤖 **智能问数**：自然语言 → 指标 → 维度 → 时间过滤 → 取数，一句话拿报表，指标口径统一维护。

## 七、写在最后

回到开头那个问题："最近差评里到底在骂什么？"

过去，这个问题的答案取决于**有没有人愿意花一周时间去导数据、打标签**。
现在，它应该是一个可以随时点开、随时下钻、随时换口径的看板。

大模型真正改变数据平台的地方，不是多了一个聊天窗口，而是：

> **非结构化数据第一次可以不经过人工和定制模型，直接变成数仓里可聚合的字段。**
>
> 而它进入数仓最自然的方式，不是作为一个外部服务，而是作为**数据管道里的一个转换节点**。

标签会变，业务会变。当"改一个标签"的成本从"两周"变成"改一行提示词"，数据才真正追得上业务。
