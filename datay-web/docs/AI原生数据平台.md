# AI 原生数据平台：不是加一个聊天框，而是让 AI 长进数据链路的每一环

> 这两年，「AI 数据平台」几乎成了一句正确的废话——打开任何一个数据产品，右上角都挂着一个会聊天的机器人。
>
> 但真正的分水岭不在于**有没有 AI**，而在于：AI 是长在平台里，还是贴在平台外面？

---

## 一、先泼一盆冷水：给数据平台加个聊天框，并不叫 AI 原生

我们见过太多这样的组合：

- 数据平台是老的，上面套一个「智能助手」，问一句话，它当场拼一段 SQL 去查库；
- 模型接上库才发现：`pay_amount` 和 `order_amount` 分不清、「销售额」到底算不算退款全靠它现场发挥；
- 非结构化的评价、工单、弹幕，还是只能躺在 ODS 层，靠人一周一周地导 Excel、打标签；
- 想问数，得先把数据从数仓导出去、调个外部 AI 服务、再把结果导回来；
- 权限靠提示词约束——「请不要查询其他大区的数据」。

这些做法的共同点是：**AI 被当成一个外挂服务，而不是平台的一部分。**
于是「数据集成」和「AI」各跑各的、状态断成两截、口径慢慢分叉、权限到处漏风。

**AI 原生（AI-Native）** 不是这个意思。

它指的是：AI 不再是某一个页面上的功能，而是像电工布线一样，**长进数据链路的每一段**——
数据进来时、数据加工时、数据建模时、数据被查询时、平台被操作时。

一句话概括：

> **AI 原生 = 让模型只做它该做的事（翻译与推理），其余交给平台（口径、权限、状态、幂等）。**

在 DataY 里，这件事被拆成三层来落地。下面逐一展开。

---

## 二、第一层：管道里的 AI —— 让非结构化数据真正进数仓

### 一个每周都在发生的场景

周三下午，产品经理问数据同学：

> 「最近差评里到底在骂什么？包装破损有多少？功能故障有多少？」

数据同学一看表：**只有评分和文本，没有「问题类型」字段。**
于是接下来一周：导数据 → Excel 关键字粗筛 → 人工抽样打标签 → 做 PPT。等做完，热点早换了一轮。

问题不在人，在于**传统数据管道天生只认结构化数据**。它能搬 `order_id`、`amount`，却读不懂「快递盒被压瘪了，耳机盒上有压痕」这句话。

要统计「包装破损 / 功能故障 / 客服态度」，就必须先做一件事：**把一句话，变成几个字段。**

### 关键分歧：不是让大模型当后台服务，而是让它进管道

很多团队的第一反应是：起一个独立的 AI 服务，数据从数仓导出 → 调 API → 结果导回数仓。**这个架构在真实生产里会迅速失控：**

- 多一套服务要部署、监控、扩缩容；
- 数据链路断成两截，管道跑完了 AI 还没跑完，数仓里是「半成品」；
- 失败重试、增量、幂等、背压，全部要重新实现一遍；
- 数仓指标口径和 AI 服务口径逐渐分叉。

正确的做法是：**把大模型做成数据管道里的一个转换节点**，和 Join、Filter、SQL 算子同级。

DataY 提供的这个算子叫 **`LlmComponent`（画布上叫「大模型」）**，定位只有两条：

- **按行处理**：每条用户反馈独立构造一次请求，互不干扰；
- **JSON 扩充、文本兜底**：模型返回 JSON 对象，就把字段合并进当前行；返回普通文本，就写进 `llm_result` 字段继续往下传，**脏输出不会炸掉整条流水线**。

```
评价 / 客服会话 / 售后备注 / 直播弹幕
              │
              ▼  Kafka / CDC 实时同步（数据集成）
        ┌───────────────────────────────┐
        │      VOC 流水线（流批一体）      │
        │  ODS 原文 ──▶ 【大模型节点】    │  ← 给定输出 Schema
        │                 │             │     输出结构化 JSON
        │                 ▼             │
        │            结构化字段 ──▶ 数仓事实表
        └───────────────────────────────┘
              │
              ▼
    VOC 分析宽表 ──▶ BI 看板 / 投诉趋势 / 售后热点
```

### 工程上到底跑得稳吗？

以电商 VOC 流水线为例，本地真跑一遍的结果是：

- **30 条反馈 → 22 条判定为负面，平均负面分 53.8，全链路约 25 秒**，全部落表为结构化字段；
- 模型真的读懂了语义：「拆开快递盒，包装已经瘪了一块，耳机盒有压痕」→ `包装物流 / 包装破损`，而不是误判成「商品损坏」；
- 模型区分了强弱：「插上电完全没反应」给 90 分，「包装瘪了一块」只给 60 分——这正是投诉排序需要的信号。

把大模型放进管道，难点从来不是「接得上」，而是「跑得稳、算得清」。DataY 的答案是——**复用管道已有的一切**：

| 现实问题 | 管道内 AI 的答案 |
| --- | --- |
| 逐行调用，量大了怎么办 | 上游先收敛 + 增量而非全量 + 任务级并行 |
| token 成本 | 10 万条反馈 ≈ 4000 万 token，按主流国产模型量级折算是**几十元**，单条不到千分之一元 |
| 失败怎么办 | 组件内置 `retryCount` / `retryIntervalMillis`，超时自动重试并记录异常链；解析失败落 `llm_result`，数据不丢 |
| 幂等与顺序 | 按行独立，生产上按业务主键做幂等，用增量字段控制重复消费 |
| 提示词散落怎么治理 | Schema 收敛枚举、temperature 保持低值、人工抽检、**改提示词当天生效** |

> 最关键的一点：**Schema 是一等公民。**
> 模型输出被约束成明确字段后，落表、建模、指标定义全都在同一套体系里——这才是「AI 原生」而非「AI 外挂」的本质区别。

## 三、第二层：语义层的 AI —— 问数答不准，90% 不是模型的问题

你一定见过这样的演示：把大模型接上数据库，问一句「上个月各门店销售额」，它当场写出 SQL，跑出结果，全场鼓掌。

然后你把它接进公司真实的数仓，问同一句话，它开始表演：

- 把 `pay_amount`（实付）当成 `order_amount`（应收），金额对不上财务；
- 「销售额」理解成 `SUM(price)`，忘了乘数量；
- 按门店分组时，分不清是门店编号还是门店名称；
- 「北京」这个条件，挂到了省份字段上，结果只查回一个城市；
- 换个问法问同一件事，两次答案不一样——因为它每次都在**重新理解**你的业务。

**反常识的结论：问数答不准，绝大部分不是模型不够强，而是数据侧缺少一层「业务语义」。**
模型再强，看到的也只是一堆 `t_order`、`amt`、`sk`、`flag`。它不知道「销售额」指哪个口径、「门店」是哪个字段、「上月」是按自然月还是滚动 30 天。

要让一句话问数真正可用，得先把业务语义**沉淀下来**——这就是**维度建模**和**指标管理**，它们共同的产物叫**语义一致性**。

### 维度建模：给数据装上「业务坐标系」

事实表通过外键关联各个维度表，形成「星型」结构。任何一次分析，本质都是：**选几个维度做分组，选几个事实做聚合。**

落地时有三类维度必须被「建模」出来，而不是靠人记住：

| 维度类型 | 例子 | 建模后得到什么 |
| --- | --- | --- |
| **普通维度** | 门店、商品、客户 | 指定成员 ID 作主键、指定展示字段，「按门店分组」永远落在同一字段 |
| **层级维度** | 品类（一/二/三级）、区域（大区/省/城市） | 自动生成 `levelN_id / levelN_name` 与层级路径，「按一级品类看」成为明确层级 |
| **时间维度** | 年 / 季 / 月 / 日 | 自动生成 `year_id / quarter_id / month_id / day_id` 与 `date_key`，可一键预置日期数据 |

最后把事实表的外键「指」到维度上，并指定一个时间周期字段——数据才算真正有了坐标系。

### 指标管理：让「销售额」在全公司只有一个口径

现实中的「销售额」，在不同人嘴里至少有五种口径：下单金额、支付金额、应收金额、含税/不含税、含运费/不含运费。
如果这些只存在于报表 SQL 里、分析师口口相传里，那么**每次问数，模型都会重新发明一次口径**。

DataY 把口径变成平台里的**一等公民**：

```
原子指标（绑定明细事实表，一段聚合公式）
  销售额   = SUM(order_amount)
  订单数   = COUNT(DISTINCT order_id)
  毛利     = SUM(order_amount - cost_amount)

衍生指标（用指标编码引用，不允许再写 SQL）
  毛利率   = ${gross_profit} / ${sales_amount}
  客单价   = ${sales_amount} / ${order_count}

业务限定（把条件固化进口径）
  有效销售额 = 销售额，限定 order_status = 'PAID'
```

这套设计有三个隐性收益，比「能配指标」本身更重要：

1. **口径唯一**：毛利率永远是「毛利 ÷ 销售额」，引用的是同一个定义，没人能偷偷换分母；
2. **口径可解释**：每个指标都有编码、口径描述、单位，人和 AI 看到的是同一份说明书；
3. **口径可下钻**：原子指标绑定明细事实表，任意维度、任意时间粒度都能加上去聚合。

### 语义一致性：准确率的真正来源

把维度建模和指标管理放在一起看，它们其实在做同一件事：**把「业务语言」映射到「数据语言」，并且只映射一次。**
这直接决定智能问数的天花板，体现在三个「不跑偏」：

- **指标不跑偏**：先匹配已定义的指标编码，取它的公式与业务限定，模型**不负责临时发明公式**；
- **维度不跑偏**：「按品类」「按大区」必须落到真实维度模型与字段，层级让「一级/二级品类」成为明确选择；
- **条件不跑偏**：「北京」该挂城市、省份还是大区字段？语义层里存着维度成员值，问数时先检索成员再生成过滤条件。

> 没有语义层，问数是「模型现场理解你的业务」——每次都可能不一样。
> 有了语义层，问数是「模型在你的业务坐标系里查数」——口径由你定义，模型只负责翻译和取数。

## 四、第三层：平台里的 AI —— 让 Agent 直接操作数据平台

前两层解决的是「AI 能不能读懂数据和业务」。第三层解决的是更激进的问题：

> **能不能让 AI Agent 直接操作整个数据平台？**

DataY 通过 MCP（Model Context Protocol）把平台能力暴露给 AI 客户端。接上 Claude Desktop / Cursor / DSH 之后，一句话就能驱动整条链路：

> 「把 MySQL 订单库接进来，建一个每天 2 点同步到 DuckLake 的 ETL 任务，先试跑看看数据，没问题再上线。」

Agent 的调用序列大致是：

```
datasource_create   {name:"订单库", type:"mysql", url:"jdbc:mysql://...", ...}
datasource_tables   {id:12, schema:"order_db", search:"order"}
datasource_columns  {id:12, schema:"order_db", table:"t_order"}
etl_task_create     {taskName:"订单同步", cron:"0 0 2 * * ?", nodes:[...], edges:[...]}
etl_task_debug      {id:31, rowLimit:50}     ← 试跑取数，sink 只读不写
etl_task_run        {id:31}
etl_task_online     {id:31}                  ← 上线并加入调度
```

建模、落表、问数也照样自动化：

```
data_model_create            {name:"日期维度", modelType:"DIMENSION", dimensionKind:"TIME", ...}
data_model_materialize_check {id:7, dataSourceId:1, schemaName:"dw", tableName:"dim_date"}
data_model_materialize       {id:7, ..., generateData:true}
query_metric_data            {metricCodes:["sales_amount"], dimensions:[...], conditions:[...], timeRange:{...}}
```

整条链路——**建数据源 → 建 ETL 任务并试跑 → 上线调度 → 建模并物化落表 → 一句话问指标**——不再需要手点页面。

### 但能力越大，越要有边界

MCP Harness 复用平台既有的鉴权与租户隔离，而不是另起一套：

- **传输层鉴权**：`Authorization: Bearer mcp_<userId>_<random>`，缺失或非法直接 `401`；
- **租户解析**：`X-Tenant-Id` / `X-Tenant-Code` 校验归属后写入上下文，**跨租户数据不可见**；
- **数据权限**：用户与角色写入安全上下文，行级范围与页面行为完全一致；
- **写开关**：`datay.mcp.harness.allow-mutating-tools=false` 一键降级为**只读**——写工具全部拒绝，但**指标问数能力不受影响**；
- **出参裁剪**：统一裁剪响应，数据源**永不返回密码**。

## 五、AI 原生的四条底线

把上面三层合起来看，「AI 原生数据平台」和「数据平台 + AI 外挂」的分野，可以收敛成四条底线：

**① 模型不写 SQL，只调平台接口**

智能问数链路是：`自然语言 → 四要素（指标 / 维度 / 限定 / 时间范围）→ 调平台查询接口 → 服务端生成 SQL → 执行 → 返回结构化结果`。

模型手里只有一组**只读**工具——`retrieve_metric_context`（语义检索）、`list_metrics`（口语映射到编码）、`describe_metrics`（可用维度与时间字段）、`sample_dimension_values`（确认「北京」挂哪）、`query_metric_data`（唯一数据出口，入参是结构化槽位）。

> **这个工具清单里，没有任何可以执行任意 SQL 的能力。**

带来四个直接好处：口径不可能被临时发明、权限控制点唯一、审计治理可收口、**换模型不影响口径**。

**② 数据权限长在查询接口上，不长在提示词里**

问数把取数门槛降到「会说中文就行」，这既是价值也是风险。如果靠提示词约束模型——「请不要查询其他大区的数据」——那等于**没有权限**：提示词是建议，不是边界。

DataY 的做法是把 RBAC + 维度成员范围**拼进 SQL 的 WHERE** 再执行：

- 用户怎么问，改不了它；模型怎么理解，也改不了它；
- **入口一致**：网页问数、指标查询面板、MCP 客户端走**同一个查询接口**，不存在「网页挡住了、API 没挡」的缺口；
- **失败关闭可选**：受控维度没和事实表关联时，可直接拒绝查询，而不是默默返回全量；
- **管理员例外是显式的**：这是明确的角色语义，不是「漏配」。

**③ 口径唯一，且可解释**

AI 问数、指标面板、报表用的是**同一套口径**。返回结果时会附带解析过程——命中了哪个指标、按哪个维度、加了什么条件、算了哪段时间。

> **你可以像校验同事一样校验 AI。**

**④ AI 能力可独立降级，不影响平台本体**

没配 AI API Key 时，助手自动降级为不可用，普通查询与调度不受影响；MCP 写开关一关，问数照常。**AI 是增强项，不是单点依赖。**

上述三层能力，跑在 **DataY** 上——一套开源、轻量的一体化数据平台：

> **一个 JAR、内嵌 DuckDB，2 核 4G 就能跑通「数据集成 → 数据建模 → 数据开发 → 任务调度 → 数据应用」的完整链路。**

它由「一个引擎 + 一个平台」组成：

| 模块 | 定位 | 说明 |
| --- | --- | --- |
| **DataY Core** | 数据集成引擎 | 轻量、可嵌入、流批一体；JSON 定义任务、自动建表、CDC 实时同步；可脱离 Web 独立运行或嵌入 Java 应用 |
| **DataY Web** | 可视化数据平台 | 拖拽式任务设计、Quartz 调度、维度建模、指标管理、智能问数 |

**五大能力 + 一个 AI 原生底座：**

- 🔌 **数据集成**：MySQL / PostgreSQL / Oracle / SQL Server / Doris / ClickHouse / DuckDB 等十余种数据源，MySQL Binlog、PostgreSQL WAL CDC 实时同步，自动建表与 DDL 转换；
- 📐 **维度建模**：星型 / 雪花模型，普通 / 层级 / 时间维度，事实表外键一键关联；

- 🤖 **智能问数**：自然语言 → 指标 → 维度 → 时间过滤 → 取数，一句话拿报表；
- 🧠 **AI 原生底座**：管道内的 `LlmComponent`、语义层驱动的智能问数、面向 Agent 的 MCP Harness，共用同一套口径与权限。

### 电商场景实测：一句话问数

用内置「电商销售分析应用」资产包一键初始化（数据源、9 个模型、12 个指标、11 个任务全部自动建好）后：

- 问「各一级品类的销售额和毛利率」→ 电子产品 167,738.85 元 / 29.63%；家居生活 20,990.20 元 / 32.87%；服饰鞋包 14,081.30 元 / 31.18%；

## 七、写在最后

回到最初那个行业现象：几乎每个数据平台都挂上了一个会聊天的机器人。

但真正的 AI 原生，不是**在数据平台上加一个 AI**，而是**让 AI 成为数据链路本身的一部分**：

- 在管道里，它是能把一句话变成几个字段的**转换节点**；
- 在语义层，它是只负责翻译、不负责发明口径的**取数助手**；
- 在平台上，它是能自己建源、建任务、建模、问数的 **Agent**；
- 而口径、权限、状态、幂等——**始终由平台掌控**。

过去两年，大家把大量精力花在「换更强的模型」上，却常忽略一个事实：

> **大模型解决的是「语言到意图」的问题，解决不了「意图到口径」的问题。**
> 后者只能靠数据侧的语义层。

当 AI 长进链路的每一环，而平台守住每一条底线，数据平台才真正配得上「AI 原生」这四个字。
