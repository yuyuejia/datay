# 数据应用资产包编写规范

> 资产包是 DataY 唯一的「演示数据 / 场景交付」载体：平台不再通过数据库迁移脚本预置业务数据，
> 所有业务场景（含官方演示场景）都以资产包的形式放在
> `datay-web/src/main/resources/app-packages/*.json`，由用户在市场里初始化到自己的租户。
>
> 本文是编写资产包的**唯一规范**，也是代码评审与新场景开发的依据。

---

## 0. 机制速览

- 启动时 `SystemAppPackageLoader` 扫描 `classpath*:app-packages/*.json`，按 `meta.code` 幂等登记为系统预制包。
- 用户可在「数据应用 → 应用市场」中初始化资产包，服务端逐类安装并做 **ID 替换**（详见 `数据服务应用市场.md`）。
- 包内所有对象用「包内逻辑 ID」`oldId` 标识，其它对象用 `xxxOldId` 引用；导入时统一替换成目标租户的真实 ID。
- 因此编写资产包时**只需要保证包内自洽**，不需要关心目标租户已有的 ID。

## 1. 顶层结构

```jsonc
{
  "packageFormat": "datay-app-package",   // 固定
  "formatVersion": "1.0",                 // 固定
  "meta": {
    "name": "电商销售分析应用",
    "code": "ecommerce_sales_app",        // 全局唯一，建议 <场景>_<用途>_app
    "description": "面向零售电商的销售分析应用……",
    "category": "零售电商",                // 市场按此分类，一个场景一个分类
    "version": "1.0.0",
    "source": "SYSTEM"                    // 系统预制包固定 SYSTEM
  },
  "dataSources": [], "modelDirectories": [], "models": [],
  "metricDirectories": [], "metrics": [],
  "etlTasks": [], "sqlJobs": [], "dagJobs": [], "otherJobs": [], "jobDepends": [],
  "summary": {}                           // 可省略，加载/导出时会按实际内容重算
}
```

`oldId` 是包内逻辑 ID，**同类对象内必须唯一**（`oldId` 与 Job 的 `oldId` 共用一套编号空间，见 §7）。
建议按类型分段编号，便于人工核对，例如模型目录 1000+、模型 3000+、模型字段 4000+、指标目录 2000+、
指标 2600+、ETL 任务 6000+、Job 7000+、编排 7100+、数据源 1600+。

## 2. 数据源 `dataSources`

```jsonc
{
  "oldId": 1600,
  "key": "电商数仓(DuckDB)|DUCKDB|jdbc:duckdb:./data/ecommerce.duckdb",  // 名称|类型|URL
  "name": "电商数仓(DuckDB)",
  "description": "零售电商本地数仓，维度表与事实表都落在 main schema。",
  "type": "DUCKDB",
  "url": "jdbc:duckdb:./data/ecommerce.duckdb",
  "hostname": "",
  "port": "",
  "schemaName": "main",
  "database": null,
  "username": "",
  "password": "",
  "connectionMode": null,
  "extraParams": {}
}
```

- 导入时先按 `名称 + 类型 + URL` 在目标租户里查找，命中直接复用，未命中才新建。
- 演示场景建议用本地 DuckDB 文件：**开箱即用、无需外部依赖**。
  注意 DuckDB 的 `jdbc:duckdb:./data/xxx.duckdb` 是**相对路径**，按进程工作目录解析：
  用 `java -jar datay-web/target/*.jar` 在仓库根目录启动时落在 `<仓库根>/data/`，
  用 `mvn spring-boot:run` 在 `datay-web/` 下启动时落在 `datay-web/data/`。
  一个场景通常两个数据源：**源系统（业务库）** 与 **数仓**，文件名区分，例如
  `./data/xxx_ods.duckdb`（源）与 `./data/xxx.duckdb`（数仓）。
- 若场景面向真实生产，可把源数据源写成 MySQL/PostgreSQL，但要在 `description` 里说明连接要求。

## 3. 目录 `modelDirectories` / `metricDirectories`

```jsonc
{ "oldId": 1000, "name": "01-DIM 维度层", "parentOldId": null, "sortOrder": 1 }
{ "oldId": 1002, "name": "公共维度", "parentOldId": 1000, "sortOrder": 1 }
```

- 导入时按 `名称 + 父目录` 复用已有目录，不会重复创建。
- 建议分层：模型目录用 `01-DIM 维度层` / `02-FACT 事实层`，指标目录按业务域（如 `销售指标`）。

## 4. 数据模型 `models`

```jsonc
{
  "oldId": 3002,
  "dataSourceOldId": 1600,      // 绑定数据源（必填）
  "directoryOldId": 1002,       // 所属目录（可空）
  "name": "门店维度",
  "code": "dim_store",
  "description": "零售门店主数据……",
  "modelType": "DIMENSION",     // DIMENSION / DWD / DWS / ADS
  "dimensionKind": "NORMAL",    // 仅维度模型：NORMAL / HIERARCHY / TIME
  "levelCount": null,           // 仅 HIERARCHY：层级数
  "timeFieldName": null,        // 仅事实模型：时间周期字段名
  "timeLevels": null,           // 仅 TIME：YEAR,QUARTER,MONTH,DAY（由粗到细）
  "timeStart": null, "timeEnd": null,
  "isRegistered": false,
  "project": "retail",
  "schemaName": "main",
  "tableName": "dim_store",     // 物理表名，ETL 的 ModelWrite 会写这张表
  "displayFieldName": "store_name",  // 维度默认展示字段（图表 x 轴 / 维度取值展示）
  "fields": [ /* 见 §4.1 */ ]
}
```

### 4.1 字段 `fields[]`

```jsonc
{
  "oldId": 4001, "fieldName": "store_id", "fieldType": "VARCHAR", "fieldLength": 64,
  "fieldPrecision": null, "fieldScale": null,
  "description": "门店ID", "sortOrder": 1,
  "isPartitionKey": false, "isPrimaryKey": true,
  "dimensionModelOldId": null,   // 外键：关联哪个维度模型
  "dimensionFieldOldId": null,   // 该维度模型上用于展示的字段
  "fieldRole": null,             // 生成字段的角色，见下表
  "levelIndex": null             // 层级/时间层级的层号，从 1 开始
}
```

`fieldRole` 取值：`LEVEL_ID`、`LEVEL_NAME`、`MEMBER_ID`、`MEMBER_NAME`、`HIERARCHY`（普通字段为 `null`）。

### 4.2 四种维度/模型类型的字段约定

平台前端会自动生成层级字段，资产包必须与之一致，否则维度层级分组、时间趋势等能力不生效。

#### （1）普通维度 `modelType=DIMENSION, dimensionKind=NORMAL`
只写业务字段，**必须有一个 `isPrimaryKey=true` 的成员 ID 字段**（外键连接用它），并设置 `displayFieldName`。

```jsonc
// dim_store
"fields": [
  {"oldId": 4001, "fieldName": "store_id",   "fieldType": "VARCHAR", "fieldLength": 64, "isPrimaryKey": true,  "sortOrder": 1},
  {"oldId": 4002, "fieldName": "store_name", "fieldType": "VARCHAR", "fieldLength": 128, "sortOrder": 2},
  {"oldId": 4003, "fieldName": "store_type", "fieldType": "VARCHAR", "fieldLength": 32,  "sortOrder": 3},
  {"oldId": 4004, "fieldName": "city",       "fieldType": "VARCHAR", "fieldLength": 64,  "sortOrder": 4},
  {"oldId": 4005, "fieldName": "open_date",  "fieldType": "DATE",                          "sortOrder": 5}
]
```

#### （2）层级维度 `modelType=DIMENSION, dimensionKind=HIERARCHY, levelCount=N`
必须生成：`level{i}_id` / `level{i}_name`（VARCHAR 255，`fieldRole` 分别为 `LEVEL_ID`/`LEVEL_NAME`，`levelIndex=i`）、
`member_id`（VARCHAR 255，`MEMBER_ID`，**`isPrimaryKey=true`**，取末级 ID）、`member_name`（`MEMBER_NAME`，末级名称）、
`hierarchy`（`HIERARCHY`，各层级名称由粗到细用 `/` 连接）。业务属性字段（如 `manager`）放在生成字段之前。

```jsonc
// dim_region，levelCount=3：大区 / 省 / 城市
"fields": [
  {"oldId": 4200, "fieldName": "region_manager", "fieldType": "VARCHAR", "fieldLength": 64, "sortOrder": 1},
  {"oldId": 4201, "fieldName": "level1_id",   "fieldType": "VARCHAR", "fieldLength": 255, "fieldRole": "LEVEL_ID",   "levelIndex": 1, "sortOrder": 2},
  {"oldId": 4202, "fieldName": "level1_name", "fieldType": "VARCHAR", "fieldLength": 255, "fieldRole": "LEVEL_NAME", "levelIndex": 1, "sortOrder": 3},
  {"oldId": 4203, "fieldName": "level2_id",   "fieldType": "VARCHAR", "fieldLength": 255, "fieldRole": "LEVEL_ID",   "levelIndex": 2, "sortOrder": 4},
  {"oldId": 4204, "fieldName": "level2_name", "fieldType": "VARCHAR", "fieldLength": 255, "fieldRole": "LEVEL_NAME", "levelIndex": 2, "sortOrder": 5},
  {"oldId": 4205, "fieldName": "level3_id",   "fieldType": "VARCHAR", "fieldLength": 255, "fieldRole": "LEVEL_ID",   "levelIndex": 3, "sortOrder": 6},
  {"oldId": 4206, "fieldName": "level3_name", "fieldType": "VARCHAR", "fieldLength": 255, "fieldRole": "LEVEL_NAME", "levelIndex": 3, "sortOrder": 7},
  {"oldId": 4207, "fieldName": "member_id",   "fieldType": "VARCHAR", "fieldLength": 255, "fieldRole": "MEMBER_ID",   "isPrimaryKey": true, "sortOrder": 8},
  {"oldId": 4208, "fieldName": "member_name", "fieldType": "VARCHAR", "fieldLength": 255, "fieldRole": "MEMBER_NAME", "sortOrder": 9},
  {"oldId": 4209, "fieldName": "hierarchy",   "fieldType": "VARCHAR", "fieldLength": 500, "fieldRole": "HIERARCHY",  "sortOrder": 10}
]
```
`displayFieldName` 建议设为 `member_name`。

#### （3）时间维度 `modelType=DIMENSION, dimensionKind=TIME`
`timeLevels` 由粗到细，如 `YEAR,QUARTER,MONTH,DAY`。字段必须与 `TimeGranularity` 完全一致：

| 字段 | 类型 | fieldRole | levelIndex | 取值示例 |
| --- | --- | --- | --- | --- |
| `year_id` | VARCHAR(32) | LEVEL_ID | 1 | `2024` |
| `year_name` | VARCHAR(64) | LEVEL_NAME | 1 | `2024年` |
| `quarter_id` | VARCHAR(32) | LEVEL_ID | 2 | `2024Q1` |
| `quarter_name` | VARCHAR(64) | LEVEL_NAME | 2 | `2024年Q1` |
| `month_id` | VARCHAR(32) | LEVEL_ID | 3 | `202401` |
| `month_name` | VARCHAR(64) | LEVEL_NAME | 3 | `2024-01` |
| `day_id` | VARCHAR(32) | LEVEL_ID | 4 | `20240115` |
| `day_name` | VARCHAR(64) | LEVEL_NAME | 4 | `2024-01-15` |
| `date_key` | **BIGINT** | MEMBER_ID | - | `20240115`（= 最末级 id，**isPrimaryKey=true**） |
| `hierarchy` | VARCHAR(500) | HIERARCHY | - | `2024年/2024年Q1/2024-01/2024-01-15` |

> `date_key` 用 **BIGINT（yyyyMMdd）** 而不是 DATE：指标查询的时间区间过滤会把 `yyyy-MM-dd`
> 归一化成 `yyyyMMdd` 后按数值比较，事实表的时间外键必须与之同类型。
> `displayFieldName` 建议设为 `month_name`。

#### （4）事实模型 `modelType=DWD`（原子指标只能挂在 DWD 上）
- 每个维度外键字段设置 `dimensionModelOldId`（关联维度模型）与 `dimensionFieldOldId`（该维度的展示字段）；
- 选中一个日期外键作为 `timeFieldName`（必须与 `dim_date.date_key` 同类型 BIGINT）；
- 度量字段用 `DECIMAL` + `fieldPrecision/fieldScale`，或 `LONG` 做计数。

```jsonc
// fact_sales_order（DWD）
"timeFieldName": "order_date_key",
"fields": [
  {"oldId": 4500, "fieldName": "order_id",       "fieldType": "VARCHAR", "fieldLength": 64, "sortOrder": 1},
  {"oldId": 4501, "fieldName": "order_date_key", "fieldType": "BIGINT",  "dimensionModelOldId": 3000, "dimensionFieldOldId": 4100, "sortOrder": 2},
  {"oldId": 4502, "fieldName": "store_key",      "fieldType": "VARCHAR", "fieldLength": 64, "dimensionModelOldId": 3002, "dimensionFieldOldId": 4002, "sortOrder": 3},
  {"oldId": 4503, "fieldName": "product_key",    "fieldType": "VARCHAR", "fieldLength": 64, "dimensionModelOldId": 3003, "dimensionFieldOldId": 4302, "sortOrder": 4},
  {"oldId": 4504, "fieldName": "customer_key",   "fieldType": "VARCHAR", "fieldLength": 64, "sortOrder": 5},
  {"oldId": 4505, "fieldName": "order_status",   "fieldType": "VARCHAR", "fieldLength": 32, "sortOrder": 6},
  {"oldId": 4506, "fieldName": "quantity",       "fieldType": "LONG",                            "sortOrder": 7},
  {"oldId": 4507, "fieldName": "order_amount",   "fieldType": "DECIMAL", "fieldPrecision": 18, "fieldScale": 2, "sortOrder": 8},
  {"oldId": 4508, "fieldName": "cost_amount",    "fieldType": "DECIMAL", "fieldPrecision": 18, "fieldScale": 2, "sortOrder": 9}
]
```

#### （5）DWS / ADS 汇总模型（可选）
`modelType=DWS`/`ADS` 用于展示汇总层，物理表通常由 SQL 任务生成（不参与原子指标）。字段按汇总表结构写。
**注意**：原子指标只能绑定 `DWD` 模型。

### 4.3 物理表由谁创建

| 模型 | 物理表创建方式 |
| --- | --- |
| 维度 / 事实（DWD） | ETL 任务 `StreamJdbcInput`/`SqlInput` → `ModelWrite`，表不存在时按上游元数据自动建表 |
| DWS / ADS | SQL 任务里的 `CREATE OR REPLACE TABLE ... AS SELECT ...` |

**关键约束**：源库（ODS）表的列名与类型必须与目标模型的 `fields` 完全一致，
`ModelWrite` 按上游元数据建表，列不一致会导致模型字段与物理表对不上（指标查询、智能问数会失败）。

## 5. 指标 `metrics`

```jsonc
// 原子指标
{
  "oldId": 2610, "directoryOldId": 2510,
  "name": "销售额", "code": "sales_amount",
  "description": "统计口径：已下单订单明细金额合计。",
  "metricType": "ATOMIC", "status": "ENABLED",
  "factModelOldId": 3100,                 // 必须是 DWD 模型
  "formula": "SUM(order_amount)",         // 只允许 字母数字_ + - * / ( ) . , % 和单引号
  "unit": "元", "dataType": "DECIMAL", "isAdditive": true,
  "filterConfig": null                    // 业务限定，见下
}
```

```jsonc
// 衍生指标：公式只允许 数字、+ - * / ( )、空白 与 ${指标编码}
{
  "oldId": 2620, "directoryOldId": 2510,
  "name": "毛利率", "code": "gross_profit_rate",
  "description": "毛利 / 销售额。",
  "metricType": "DERIVED", "status": "ENABLED",
  "formula": "${gross_profit} / ${sales_amount}",
  "unit": "%", "dataType": "DECIMAL", "isAdditive": false
}
```

业务限定 `filterConfig` 是 **JSON 对象**（不是字符串）：

```jsonc
"filterConfig": {
  "conditions": [
    { "type": "FACT_FIELD", "factFieldName": "order_status", "operator": "EQ", "value": "PAID", "logic": "AND" }
  ]
}
```
- `type`：`FACT_FIELD`（事实表字段）/ `DIMENSION`（关联维度字段，需 `dimensionModelId` + `dimensionModelCode` + `dimensionFieldName`）/ `TIME`
- `operator`：`EQ/NE/GT/GE/LT/LE/IN/NOT_IN/LIKE/IS_NULL/IS_NOT_NULL/BETWEEN`
- `FACT_FIELD`/`TIME` 的字段必须真实存在于事实模型字段列表中。

**指标编码在包内必须唯一**，衍生指标引用的编码必须在同一包内存在。

## 6. ETL 任务 `etlTasks`

```jsonc
{
  "oldId": 6001, "jobOldId": 7001,          // jobOldId：该 ETL 任务的调度 Job 的逻辑 ID，供编排引用
  "taskName": "同步门店维度", "taskCode": "ec_etl_dim_store",
  "taskDesc": "源库 ods_store → 数仓 dim_store",
  "dir": "/零售电商/维度同步", "type": "ETL", "cron": "0 0 2 * * ?", "project": "retail",
  "nodes": [ /* 见下 */ ],
  "edges": [ { "oldId": 5201, "name": "", "code": "e1", "source": "n1", "target": "n2", "config": null, "status": "0" } ]
}
```

节点：

```jsonc
{ "oldId": 5101, "label": "读取门店(源库)", "code": "n1", "desc": "", "type": "StreamJdbcInput",
  "config": { "sourceId": 1601, "schema": "main", "table": "ods_store" },
  "xAxis": "120", "yAxis": "120", "status": "0" }

{ "oldId": 5102, "label": "写入门店维度", "code": "n2", "desc": "", "type": "ModelWrite",
  "config": { "modelId": 3002, "model": "overwrite" },
  "xAxis": "480", "yAxis": "120", "status": "0" }
```

- `config.sourceId`：**源库数据源的 oldId**（导入时自动替换成新 ID）。
- `config.modelId`：**目标模型的 oldId**（导入时自动替换）。
- 连线 `source`/`target` 用节点 `code`；一条边的 `source` → `target` 表示数据流向。
- 常见节点类型：

| 类型 | 用途 | 主要 config |
| --- | --- | --- |
| `StreamJdbcInput` | 从 JDBC 数据源整表/条件抽取（支持多表、全量/增量） | `sourceId`, `schema`, `table`, `where`, `incrColumn` |
| `SqlInput` | 从 JDBC 数据源按自定义 SQL 抽取（可 JOIN） | `sourceId`, `schema`, `sql` |
| `ModelWrite` | 写入数据模型绑定的物理表（表不存在自动建表） | `modelId`, `model`: `overwrite`/`append`/`update` |
| `DuckDBWrite` | 直接写入 DuckDB 表（不依赖模型） | `table`, `model`, `autoCreateTable` |

> ⚠️ **输入组件请用 `StreamJdbcInput`**：引擎里的 `JdbcInput` 类虽然存在，但其 `@ComponentRegister`
> 已被注释，未注册到组件工厂，写成 `JdbcInput` 会在运行时报「组件初始化失败: JdbcInput」。
> 设计器里的「数据源输入」节点就是 `StreamJdbcInput`，配置项与本文一致。
> 校验方法：`GET /api/etl-components/catalog` 返回的 `code` 才是可用的组件类型。

**推荐的标准流程**：`StreamJdbcInput`（或 `SqlInput`）→ `ModelWrite`。
`model: "overwrite"` 表示每次运行前清空目标表，适合维度全量同步。

## 7. SQL 任务 `sqlJobs` / 编排任务 `dagJobs` / 其它任务 `otherJobs`

三者结构相同（`AppPackageJob`），用 `type` 区分：

```jsonc
// SQL 任务
{
  "oldId": 7010, "jobName": "初始化源库样例数据", "jobGroup": "datafusion", "type": "SQL",
  "cron": "0 0 1 * * ?",
  "jobContext": { "dataSourceId": 1601, "schema": "main", "sql": "CREATE OR REPLACE TABLE ods_store AS SELECT ...; " },
  "status": "OFFLINE", "project": "retail"
}
```
- `jobContext.dataSourceId`：在**哪个数据源**上执行（源库或数仓的 oldId）。
- `sql` 支持分号分隔的多条语句。演示场景可用 SQL 任务生成样例源数据与 ADS 汇总表。

```jsonc
// 编排任务
{
  "oldId": 7100, "jobName": "电商日更编排", "jobGroup": "datafusion", "type": "DAG",
  "cron": "0 0 3 * * ?",
  "jobContext": {
    "jobs": [ { "id": 7010 }, { "id": 7001 }, { "id": 7002 } ],
    "jobDepends": [
      { "parentJobCode": 7010, "childJobCode": 7001, "lastInterval": 0 },
      { "parentJobCode": 7001, "childJobCode": 7002, "lastInterval": 0 }
    ],
    "nodeLayout": [
      { "jobId": 7010, "label": "初始化源库样例数据", "xAxis": 80,  "yAxis": 200 },
      { "jobId": 7001, "label": "同步门店维度",       "xAxis": 380, "yAxis": 120 }
    ]
  },
  "status": "OFFLINE", "project": "retail"
}
```
- `jobs[].id` / `jobDepends` 的父子编码 / `nodeLayout[].jobId` 都指向**同包内**的 Job 逻辑 ID：
  SQL 任务用 `sqlJobs[].oldId`，编排任务用 `dagJobs[].oldId`，ETL 任务用 `etlTasks[].jobOldId`。
- 执行时按拓扑序串行执行；A → B 表示 A 成功后才跑 B。
- **所有重要任务都应被同一个编排任务串起来**，用户初始化后「跑一次编排」即可完成一次完整加工。

`otherJobs` 用于 Shell/Spark/Flink 等其它类型任务（`type` 写真实类型），演示场景一般留空。

> **顶层 `jobDepends` 建议留空。** 它对应「任务定义」里的父子依赖调度：任务被**上线调度**时，
> 调度器要求父任务在 `lastInterval` 毫秒内成功，否则子任务会一直停留在「等待中」；
> 写 `lastInterval: 0` 几乎永远不满足。资产包里的任务依赖请统一用**编排任务的
> `jobContext.jobDepends`** 表达（编排会按拓扑序自己拉起子任务），不要去填顶层 `jobDepends`。

## 8. 命名与冲突

- 导入时若目标租户已存在同 `code` 的模型/指标、同 `taskCode` 的 ETL 任务、同 `jobName` 的任务，
  默认按 `RENAME` 策略自动加 `_copy` / `(副本)` 后缀，引用同步改写；用户也可选择 `SKIP`。
- 为避免多个场景包互相干扰，建议**场景内编码加场景前缀**：
  业务场景包用语义化编码（`dim_store`、`sales_amount`）；
  教学/入门类场景包加短前缀（`qs_dim_store`、`qs_sales_amount`）。

## 9. 交付前必须完成的校验

1. **JSON 合法**：`python3 -c "import json,sys;json.load(open(sys.argv[1]))" app-packages/xxx.json`
2. **引用自洽**：写脚本检查
   - `dataSourceOldId` / `directoryOldId` / `parentOldId` / `factModelOldId` / `dimensionModelOldId` /
     `dimensionFieldOldId` 全部可解析；
   - 各类 `oldId` 唯一；
   - 衍生指标 `${code}` 引用的指标存在；
   - ETL 节点 `config.sourceId` / `config.modelId` 可解析，连线两端节点存在，节点 `type` 在组件目录中存在；
   - DAG 的 `jobs[].id`、`jobDepends`、`nodeLayout[].jobId` 都能对应到包内 Job。
3. **SQL 可执行**：把 SQL 任务的语句在对应 DuckDB 文件上真跑一遍（`python3 -c "import duckdb; ..."`），
   确认建表成功、列名与目标模型字段一致。
4. **回归测试**：`mvn -Dtest=AppPackagePresetTest test` 会校验所有预置包的格式与引用完整性。
5. **实测初始化**：启动后端 → 应用市场 → 初始化该包 → 运行编排任务 → 检查数仓表与指标查询。
