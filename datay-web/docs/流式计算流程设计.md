# 从 Binlog 到宽表：一条流式计算链路的流程设计

## MySQL CDC → JDBCLookup → StreamSQL → 目标表，四个组件把“同步”做成“计算”

> 很多团队做实时同步，做到最后只是把 A 表搬到 B 表。
> 真正的实时链路，应该在路上就把数据算好。

本文以 MySQL → MySQL 为例；换成 Doris、ClickHouse、DuckDB，只需要替换输入/输出组件，中间的补维和 SQL 计算不变。

---

### 01 业务场景：订单宽表，等不起 T+1

假设我们在做一个电商数据平台，有三个库：

- 订单库 `shop`，核心表 `order_info`，只存 `customer_id`，不存客户名称；
- 客户库 `crm`，核心表 `customer`，存客户名称、会员等级、区域；
- 分析库 `dws`，需要一张 `order_wide` 订单宽表，给实时看板、风控和运营使用。

订单表：

```sql
CREATE TABLE order_info (
  order_id     BIGINT PRIMARY KEY,
  customer_id  BIGINT,
  product_id   BIGINT,
  quantity     INT,
  unit_price   DECIMAL(12,2),
  discount     DECIMAL(12,2),
  status       VARCHAR(20),
  created_at   DATETIME,
  updated_at   DATETIME
);
```

客户表：

```sql
CREATE TABLE customer (
  id           BIGINT PRIMARY KEY,
  name         VARCHAR(64),
  member_level VARCHAR(16),
  region       VARCHAR(32),
  status       TINYINT
);
```

目标宽表：

```sql
CREATE TABLE order_wide (
  order_id              BIGINT PRIMARY KEY,
  customer_id           BIGINT,
  customer_name         VARCHAR(64),
  customer_member_level VARCHAR(16),
  customer_region       VARCHAR(32),
  product_id            BIGINT,
  quantity              INT,
  unit_price            DECIMAL(12,2),
  discount              DECIMAL(12,2),
  pay_amount            DECIMAL(12,2),
  order_level           VARCHAR(16),
  status                VARCHAR(20),
  created_at            DATETIME,
  updated_at            DATETIME
);
```

需求可以概括成四句话：

1. 订单新增、修改、删除，宽表要秒级跟上；
2. 宽表要带客户名称、会员等级、区域；
3. 要计算实付金额和订单分层；
4. 不能给订单库增加业务负担。

看起来只是“把订单表同步过去”，但真正做起来，至少有三类问题：

- **跨库**：订单和客户不在一个库，甚至不在一个实例；
- **要计算**：宽表不是原样复制，金额和分层要在链路上算出来；
- **要保序、要能恢复**：新增、更新、删除都不能丢，任务重启后还要从断点继续。

常见的三种做法：

| 方案 | 延迟 | 对业务的侵入 | 主要问题 |
| --- | --- | --- | --- |
| 应用双写 | 低 | 高 | 订单事务里多一次写库，一致性难保证 |
| 定时批同步 | T+1 | 低 | 看板滞后，全表扫描成本高 |
| 流式管道 | 秒级 | 低 | 需要认真设计事件语义、顺序和恢复 |

这个场景适合第三种：**MySQL CDC 接入 → 跨库补维 → SQL 计算 → 按事件写出**。

### 02 整体流程：把链路拆成四段

```text
        shop.order_info
              │
              │ Binlog（ROW / FULL）
              ▼
     ┌──────────────────┐
     │ MySQLBinlogInput │  接入：位点、快照、表过滤
     └────────┬─────────┘
              │ FlowFile
              ▼
     ┌──────────────────┐        crm.customer
     │    JDBCLookup    │ ◀────  批量 IN 查询
     └────────┬─────────┘
              │ 补上 customer_* 字段
              ▼
     ┌──────────────────┐
     │  StreamSqlUnit   │  DuckDB 行级计算
     └────────┬─────────┘
              │ pay_amount / order_level
              ▼
     ┌──────────────────┐
     │ StreamJdbcOutput │  auto：INSERT / UPDATE / DELETE
     └────────┬─────────┘
              ▼
        dws.order_wide
```

四段职责很清晰：

| 阶段 | 组件 | 做什么 | 设计重点 |
| --- | --- | --- | --- |
| 接入 | `MySQLBinlogInput` | 解析 Binlog，生成数据流 | 位点、快照、过滤、事件合并 |
| 补维 | `JDBCLookup` | 批量查客户表，回填字段 | 批量、前缀、缓存、关联方式 |
| 计算 | `StreamSqlUnit` | 用 DuckDB SQL 做加工 | 保持 1:1、类型、表达式 |
| 写出 | `StreamJdbcOutput` | 按事件类型写目标表 | auto、主键、幂等、顺序 |

这四段不是随便排的。补维放在计算之前，SQL 才能直接使用客户等级；计算保持行级 1:1，写出才能继续沿用 CDC 的事件语义。

### 03 流程设计的六个关键点

#### 1. 事件语义不能丢

CDC 流里传递的不只是数据，还有“这条数据发生了什么”。

DataY 用 FlowFile 承载数据，关键属性有：

| 属性 | 作用 |
| --- | --- |
| `_eventType` | `INSERT` / `UPDATE` / `DELETE` / `QUERY` |
| `_tableMetadata` | 表名、字段、类型、主键等元数据 |
| `statusMap` | Binlog 位点等断点信息 |

`JDBCLookup` 会把上游属性整体复制到输出 FlowFile；`StreamSqlUnit` 会显式保留 `_eventType`。所以这条链路走到 Sink，Sink 仍然知道当前数据是新增、修改还是删除。

这是 `model=auto` 能工作的前提。

反过来，如果中间自己写代码把数据转成普通 JSON，把 `_eventType` 丢了，Sink 就只能全部按 INSERT 处理，更新会变成重复插入，删除永远不会生效。

还有一个细节：`StreamSqlUnit` 输出元数据时，表名会变成 `tmp_<组件ID>`。所以 Sink 必须显式配置目标表名，不能依赖上游表名自动透传。

#### 2. 补维放在计算之前

`customer_id` 只是一个数字。补维之后，记录里才有 `customer_name`、`customer_member_level`、`customer_region`。

放在 SQL 之前有三个好处：

- SQL 里可以直接用会员等级、区域做业务规则，比如金卡折扣、区域包邮；
- 计算组件只关心表达式，不需要再访问外部库；
- 维表字段和订单字段在同一行里，排查问题更直观。

补维的代价是要访问另一个库。`JDBCLookup` 的做法是：

- 把本批记录的 `customer_id` 去重；
- 按 `batchSize` 拼成 `IN (?, ?, ...)` 批量查询；
- 默认 `LEFT`，没匹配到客户的订单仍然保留；
- 回填字段加 `customer_` 前缀，避免和订单同名字段冲突。

#### 3. SQL 只做行级加工，不做聚合和过滤

这条链路里，`StreamSqlUnit` 只做三件事：

- 计算实付金额；
- 计算订单分层；
- 把需要的字段整理成目标表结构。

它不做 `GROUP BY`，也不做 `WHERE` 过滤。

原因不是 SQL 不支持，而是**聚合和过滤会破坏 CDC 的事件语义**：

- 一条 `DELETE` 事件如果被 `WHERE` 过滤掉，目标表里对应的行就永远删不掉；
- 一批 `UPDATE` 事件如果被 `GROUP BY` 合成一行，Sink 拿到的还是 `_eventType=UPDATE`，但已经不知道该更新哪条主键；
- 聚合后的结果更适合追加写入，不适合沿用逐条更新/删除。

所以设计上要守住一条线：

> 明细链路保持 1:1，聚合需求另开分支。

如果确实需要实时汇总，可以在 `StreamSqlUnit` 后面接第二个 Sink，用 `append` 或 `overwrite` 写到汇总表，和明细宽表分开。

#### 4. 写出要幂等，目标表必须有主键

`StreamJdbcOutput` 的 `auto` 模式会按 `_eventType` 选择动作：

| 事件 | 写入动作 |
| --- | --- |
| `INSERT` | `INSERT` |
| `UPDATE` | 按主键 `UPDATE` |
| `DELETE` | 按主键 `DELETE` |
| `QUERY` / `DDL` | 执行 `_query` 中的 SQL |

这里有一个容易被忽略的前提：**目标表要有主键**。

没有主键时，`DELETE` 会退化成用所有列做匹配。经过 SQL 计算之后，某些列的值可能和源库不完全一致，删除就可能匹配不到任何行。

生产环境建议：

- 目标表提前建好，显式定义主键；
- 不要完全依赖自动建表，尤其是经过 SQL 加工之后的宽表；
- 接受“至少一次”语义，用主键写入保证最终幂等。

任务失败重启时，位点会回到最后一次持久化的位置，少量数据可能重复。只要 Sink 是按主键更新/删除，重复执行不会产生重复行。

#### 5. 顺序、并行和背压要一起考虑

DataY 的执行模型是：每个组件可以配置自己的 `parallelism`，组件之间用有界阻塞队列连接，队列容量默认是 10 个批次，也可以按连线单独配置。

这带来两个直接结论：

- **并行度不是越大越好**。总线程数是所有组件并行度之和，并行度高会放大目标库写入压力；
- **同一主键的事件不能乱序**。CDC 链路建议整条链路先用 `parallelism=1`，保证事件按 Binlog 顺序处理；确认瓶颈后，再考虑拆分表或按主键分区。

队列有界，天然形成背压：下游写不动，上游就会被阻塞，不会无限堆内存。

另外，CDC 输入会把相邻的、同表同类型的 `INSERT` / `UPDATE` / `DELETE` 事件合并成一个 FlowFile，最多 10000 条。批量大了吞吐高，但延迟也会增加，需要根据业务在“快”和“省”之间取平衡。

#### 6. 状态和断点要跟着数据流走

Binlog 位点不是单独存一份就完事，它要和数据一起流动。

DataY 的做法是：CDC 输入把 `binlogFile`、`binlogPosition` 放进 FlowFile 的 `statusMap`，一路传到 Sink；Sink 写成功后，由引擎持久化状态。任务重启时，从最后一次保存的位点继续。

首次运行可以打开 `snapshot=true`：

1. 先按配置的表范围读一遍历史全量；
2. 记录起始位点；
3. 再切换到增量 Binlog。

这样新任务上线时不需要手工导数，也不会漏掉快照期间发生的变更。

还有一个小坑：多个 CDC 任务连同一个 MySQL 实例时，`serverId` 必须唯一。默认值是 1000，第二个任务要改成 1001、1002，否则会互相踢下线。

把上面六点收成一句话：

> 接入不改数据，补维只加字段，计算保持 1:1，写出尊重事件。

### 04 四段怎么配

#### 4.1 接入：MySQLBinlogInput

先确认源库满足条件：

```sql
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'binlog_format';
SHOW VARIABLES LIKE 'binlog_row_image';

-- my.cnf
[mysqld]
server-id=1
log-bin=mysql-bin
binlog-format=ROW
binlog-row-image=FULL
```

账号需要复制权限：

```sql
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'cdc'@'%';
```

组件配置（`sourceId` 是数据源 ID，在 Web 设计器里就是选择一个已注册的数据源）：

```json
{
  ".id": "cdc_order",
  ".name": "MySQLBinlogInput",
  "sourceId": "shop_ds",
  "databaseNamePattern": "shop",
  "tableNamePattern": "order_info",
  "snapshot": true,
  "snapshotFetchSize": 5000,
  "serverId": 1001
}
```

几个参数的含义：

| 参数 | 说明 |
| --- | --- |
| `databaseNamePattern` | 库名正则，这里只采集 `shop` |
| `tableNamePattern` | 表名正则，这里只采集 `order_info` |
| `snapshot` | 首次运行先全量再增量 |
| `snapshotFetchSize` | 快照分批大小 |
| `serverId` | 伪装从库的 ID，多任务必须唯一 |

建议开启 `binlog_row_image=FULL`。这样 `DELETE` 事件也会带完整行镜像，补维和计算拿到的字段更完整。

#### 4.2 补维：JDBCLookup

```json
{
  ".id": "lookup_customer",
  ".name": "JDBCLookup",
  "sourceId": "crm_ds",
  "schema": "crm",
  "table": "customer",
  "localField": "customer_id",
  "lookupField": "id",
  "selectColumns": "name, member_level, region",
  "outputPrefix": "customer_",
  "joinType": "LEFT",
  "where": "status = 1",
  "cache": true,
  "batchSize": 500
}
```

这段配置做了几件事：

- 用上游的 `customer_id` 关联 `crm.customer.id`；
- 只取 `name`、`member_level`、`region` 三个字段；
- 回填时统一加 `customer_` 前缀，得到 `customer_name`、`customer_member_level`、`customer_region`；
- `LEFT` 保证客户不存在时订单不丢；
- `where status = 1` 只关联有效客户；
- 每批最多 500 个关联键，命中缓存的不再查库。

使用建议：

1. 关联字段一定要有索引；
2. 只要关联表和上游可能重名，就配 `outputPrefix`；
3. 维表实时性要求高时关闭 `cache`；
4. 订单、日志类主数据用默认的 `LEFT`，不要轻易用 `INNER`。

#### 4.3 计算：StreamSqlUnit

```sql
SELECT
  order_id,
  customer_id,
  customer_name,
  customer_member_level,
  customer_region,
  product_id,
  quantity,
  unit_price,
  discount,
  ROUND(quantity * unit_price - discount, 2) AS pay_amount,
  CASE
    WHEN quantity * unit_price - discount >= 1000 THEN 'HIGH'
    WHEN quantity * unit_price - discount >= 300  THEN 'MEDIUM'
    ELSE 'LOW'
  END AS order_level,
  status,
  created_at,
  updated_at
FROM order_info
```

组件配置很简单：

```json
{
  ".id": "calc_order",
  ".name": "StreamSqlUnit",
  "sql": "SELECT order_id, customer_id, customer_name, customer_member_level, customer_region, product_id, quantity, unit_price, discount, ROUND(quantity * unit_price - discount, 2) AS pay_amount, CASE WHEN quantity * unit_price - discount >= 1000 THEN 'HIGH' WHEN quantity * unit_price - discount >= 300 THEN 'MEDIUM' ELSE 'LOW' END AS order_level, status, created_at, updated_at FROM order_info",
  "parallelism": "1"
}
```

说明两点：

- SQL 里的 `order_info` 就是上游表名。`StreamSqlUnit` 会把上游数据写入 DuckDB 临时表，再用这条 SQL 查询；
- 这里只做表达式计算，行数不变，`INSERT` / `UPDATE` / `DELETE` 的事件数量也不会变。

`StreamSqlUnit` 基于内嵌 DuckDB，字符串、日期、窗口函数、类型转换都能用。但在这条链路里，建议克制：**能行级完成的，不要聚合；能加字段的，不要改行数。**

#### 4.4 写出：StreamJdbcOutput

```json
{
  ".id": "sink_order",
  ".name": "StreamJdbcOutput",
  "sourceId": "dws_ds",
  "schema": "dws",
  "table": "order_wide",
  "model": "auto",
  "parallelism": "1"
}
```

关键配置只有三个：

| 配置 | 说明 |
| --- | --- |
| `schema` / `table` | 明确指定目标表，不依赖上游表名 |
| `model` | `auto`，按 `_eventType` 自动选择 INSERT / UPDATE / DELETE |
| `parallelism` | CDC 链路建议从 1 开始，确认目标库能力后再调 |

再次强调：`order_wide` 最好提前建好，并带主键。

### 05 把四个组件连起来

```json
"connections": [
  { "sourceId": "cdc_order",       "targetId": "lookup_customer" },
  { "sourceId": "lookup_customer", "targetId": "calc_order" },
  { "sourceId": "calc_order",      "targetId": "sink_order" }
]
```

一条实时链路就搭好了：

```text
cdc_order → lookup_customer → calc_order → sink_order
```

在 DataY Web 里，这四步就是拖四个节点、连三条线；在 DataY Core 里，组件和连线会序列化成同样的 JSON，数据源在执行前展开成连接信息。

### 06 跑起来是什么效果

在源库执行几条 SQL：

```sql
-- 新增三笔订单
INSERT INTO order_info
VALUES
  (1001, 2001, 3001, 2, 500.00, 50.00, 'PAID', NOW(), NOW()),
  (1002, 2002, 3002, 1, 300.00, 50.00, 'PAID', NOW(), NOW()),
  (1003, 2003, 3003, 1, 300.00, 50.00, 'PAID', NOW(), NOW());

-- 修改 1001
UPDATE order_info
SET quantity = 3, discount = 100.00, updated_at = NOW()
WHERE order_id = 1001;

-- 删除 1002
DELETE FROM order_info WHERE order_id = 1002;
```

宽表最终得到的行：

| order_id | customer_name | customer_member_level | customer_region | pay_amount | order_level |
| --- | --- | --- | --- | --- | --- |
| 1001 | 张伟 | 金卡 | 华东 | 1400.00 | HIGH |
| 1003 | 李娜 | 银卡 | 华北 | 250.00 | LOW |

`1001` 先插入、后更新，最终金额是 `3 × 500 - 100 = 1400`，分层为 `HIGH`；`1002` 被删除后，宽表里不再保留。

日志里能看到这样的过程：

```text
关联查询完成，输入 3 条，输出 3 条
已成功写入 3 条记录到表 order_wide，写入模式：INSERT
...
已成功写入 1 条记录到表 order_wide，写入模式：UPDATE
已成功写入 1 条记录到表 order_wide，写入模式：DELETE
```

从 Binlog 产生到宽表可见，通常在秒级。具体延迟取决于事件合并批量、网络和目标库写入能力。

### 07 几个边界，提前想清楚

#### 1. DDL 不要直接透传到宽表

源表叫 `order_info`，目标表叫 `order_wide`。源库的 `ALTER TABLE order_info ...` 如果直接透传，目标库改的不是同一张表。

宽表链路建议：

- 结构变更走数据模型/发布流程；
- 只做同名表同步时，才考虑把 `QUERY` 事件旁路到目标库；
- 不要让 DDL 事件混进补维和计算节点，否则会在补维节点被静默丢弃，而且不会报错。

#### 2. 聚合和明细不要共用一条链路

聚合会改变行数和主键语义。明细链路保持 1:1，聚合另开分支、另配 Sink，是更稳妥的做法。

#### 3. 维表缓存没有 TTL

`JDBCLookup` 的缓存是 LRU，任务运行期间一直有效，不会自动过期。客户等级、区域这类字段如果要求强实时，建议关闭缓存。

#### 4. 并行度会打破顺序

同一订单的 `INSERT` 和 `UPDATE` 如果被两个线程同时处理，写出的先后顺序无法保证。CDC 链路先把 `parallelism` 设为 1，确认瓶颈后再考虑按主键分区。

#### 5. 目标表主键是底线

没有主键，`UPDATE` / `DELETE` 的定位条件会退化，性能和正确性都不可控。

#### 6. Binlog 保留时间要覆盖故障恢复窗口

如果 Binlog 被清理，任务又停了很久，就无法从原点位恢复。需要监控 Binlog 保留时间和任务延迟。

### 08 关于 DataY

上面这套流程不是伪代码。`MySQLBinlogInput`、`JDBCLookup`、`StreamSqlUnit`、`StreamJdbcOutput` 都来自 DataY。

DataY 是一套**极致轻量的数据平台**，理念很简单：

> 数据平台可以很小，功能不打折。

传统数据平台往往需要 Hadoop、Spark、Flink、ClickHouse 一整套组件，几十台机器起步，运维门槛高。DataY 选择另一条路：

- **一个 JAR，自研流批一体处理引擎，拒绝组件地狱；
- **2 核 4G** 就能跑通数据集成 → 数据建模 → 数据开发 → 任务调度 → 数据应用；
- 零依赖启动，10 分钟搭好开发环境；
- 调度 master 与执行 worker 可分可合，单机和集群同一套代码。

这里的“轻量”指的是**运行资源门槛低**，不是能力轻量。它不依赖 Hadoop、Spark 这类重型组件。支持 DuckDB 作为高性能分析引擎，也支持 Doris，CLickHouse等分析引擎。开发机 2 核 4G 就能跑通从数据接入到报表查询的完整链路。

DataY 由两块组成：

| 模块 | 定位 | 说明 |
| --- | --- | --- |
| **DataY Core** | 数据集成引擎 | 轻量、可嵌入、可扩展、流批一体；JSON 定义任务、自动建表、CDC 实时同步；可脱离 Web 独立运行或嵌入 Java 应用 |
| **DataY Web** | 可视化数据平台 | 拖拽式任务设计、任务调度、维度建模、指标管理、智能问数 |

和这条实时链路相关的能力：

- 🔌 **多数据源**：MySQL / PostgreSQL / Oracle / SQL Server / SAP HANA / Doris / ClickHouse / DuckDB 等；
- 🔄 **四种 CDC**：MySQL Binlog、PostgreSQL WAL、Oracle LogMiner、MongoDB Change Streams；
- 🧩 **统一组件模型**：Source / Operator / Sink，批流共用；
- 🛡️ **断点续传**：Binlog 位点、LSN、SCN、resumeToken 统一持久化；
- 🏗️ **自动建表**：跨库 DDL 转换，表不存在时自动创建；
- 🚀 **内嵌 DuckDB**：SQL 加工不需要额外计算集群；
- ⏰ **任务调度**：Quartz Cron 精确到秒，DAG 拓扑编排；
- 📦 **可嵌入**：Core 可以作为 Java 库，嵌进你自己的应用。

**快速开始：**

```bash
git clone https://gitee.com/yuyuejia/datay
cd datay
mvn clean package -DskipTests
java -jar datay-web/target/*.jar --DATAY_AI_API_KEY=sk-xxxxxxxxx
# 浏览器打开 http://localhost:8080，默认账号 admin/admin
```

也可以只用 Core：

```bash
java -jar datay-core/target/datay-core-*-jar-with-dependencies.jar taskConfig.json
```
