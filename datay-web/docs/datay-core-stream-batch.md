# 一条数据流，两种时间尺度：DataY 流批一体引擎拆解

> 摘要：批处理面对的是「有边界的数据」，流处理面对的是「没有终点的变化」。DataY 没有为两者各造一套引擎，而是用同一套 FlowFile 数据模型、同一套组件运行时、同一套状态机制，把全量、增量与 CDC 实时同步收进同一条数据流。

---

## 01 流批一体，难的不是「都能跑」

数据集成工具最容易给人一种错觉：只要既能执行一次性同步，又能启动一个 CDC 任务，就算流批一体了。

真正做过生产链路的人知道，难点在别处：

- 批任务跑完就结束，流任务却要长期驻留，运行时的生命周期完全不同；
- 批任务关心「读了多少行」，流任务关心「位点推进到哪里」；
- 批任务失败可以整段重跑，流任务失败必须知道「从哪儿接着跑」；
- 批任务的算子是「读完再算」，流任务的算子是「来一批算一批」；
- 两套引擎意味着两套组件、两套配置、两套监控、两套排障经验。

所以流批一体的价值，不是功能表上多打一个勾，而是**让同一份数据、同一套处理逻辑、同一套运维方式，在不同时间尺度上成立**。

DataY 的选择很克制：不去造一个 Flink 式的通用流计算平台，而是把「数据集成」这件事做深——用一条统一的数据流，覆盖全量同步、增量同步、CDC 实时同步，以及链路中的轻量计算。

这篇文章不讲安装和配置，而是拆开引擎内部，看看一条数据从进入任务到写入目标，究竟经过了什么。

## 02 引擎全景：一个 JAR 里的三层结构

DataY 的运行时可以分成三层。图例约定：方括号表示组件节点，圆括号表示有界队列，箭头表示数据流向。

```text
[任务定义] 可视化画布 / JSON
      │
      ▼
[DAG 解析] 拓扑排序 / 分层
      │
      ▼
[执行运行时] 线程池 + 有界队列 + 状态
      │
      ├────────────┬────────────┐
      ▼            ▼            ▼
 [Source]     [Operator]     [Sink]
      │            │            │
      └────────────┼────────────┘
                   ▼
        [FlowFile] 数据 + 表结构 + 属性 + 状态
                   │
          ┌────────┴────────┐
          ▼                 ▼
   [内嵌 DuckDB]       [外部系统]
   临时计算 / 落库      MySQL / Doris / DuckLake / MinIO
```

最上面是任务定义层。无论任务来自可视化画布还是手写配置文件，最终都会变成同一份描述：一组组件节点，加上一组连接线。节点声明「我是谁、我做什么」，连接线声明「数据从谁流向谁」。

中间是执行运行时。它负责把图变成可运行的线程、队列和状态，处理并发、背压、结束信号、异常取消与断点恢复。

最下面是组件与存储。输入组件负责把外部世界的数据翻译成 FlowFile，处理组件负责加工，输出组件负责把 FlowFile 写回外部世界。DuckDB 则既是计算引擎，也是任务内部的临时数据交换站。

三层之间没有隐藏的「魔法层」。理解这条主线，基本就理解了 DataY。

## 03 核心抽象：FlowFile 是流批统一的最小单位

DataY 里最重要的对象不是表，也不是行，而是 **FlowFile**。

一个 FlowFile 不是「一行数据」，而是一个**批次信封**。它通常包含四类信息：

| 组成 | 作用 |
| --- | --- |
| 数据体 | 一批 JSON 记录，或 JSON 对象、CSV、文本、二进制 |
| 表结构 | 字段名、字段类型、所属库表，供下游自动建表与类型转换 |
| 链路属性 | 表名、库名、事件类型、时间戳、批次序号等 |
| 状态 | 增量水位、CDC 位点、消费 offset 等断点信息 |

这个设计有两个直接好处。

第一，**批次是流批共同的语言**。批处理天然按批读取，流处理也可以把连续变更聚合成微批。下游组件看到的永远是「一个 FlowFile」，不需要知道自己处在批任务还是流任务里。

第二，**状态跟着数据走**。水位和位点不是某个全局变量的私产，而是随 FlowFile 沿 DAG 向下游传递。只有当下游真正写入成功，状态才在 Sink 处被提交。这是后面所有恢复语义的基础。

组件则被分成三类：

- **Source**：数据的起点，负责读取数据库、文件、HTTP 请求、消息队列或 CDC 日志；
- **Operator**：数据的加工者，负责 SQL、脚本、字段映射、路由、调用模型等；
- **Sink**：数据的终点，负责写入关系库、DuckDB、DuckLake、Doris 等目标。

连接线不是装饰。每一条连接线在运行时都会变成一条**有界阻塞队列**，这是 DataY 数据流转的物理通道。

## 04 一条数据流的完整旅程

先看一条典型的任务链路。两路输入分别进入有界队列，汇合到同一个 SQL 加工节点，加工结果再分成两个出口：

```text
[MySQL CDC] ──▶ (队列 10 批) ──┐
                               ├──▶ [SQL 加工] ──┬──▶ (队列) ──▶ [写入 DuckDB]
[文件 / HTTP] ─▶ (队列) ───────┘                 └──▶ (队列) ──▶ [写入 Doris]
```

任务启动后，引擎按下面的顺序把图跑起来。

### 第一步：解析与拓扑排序

引擎先解析节点和连线，得到一张有向无环图，再做拓扑排序。排序不是简单地把节点排成一列，而是按「层」推进：没有上游依赖的节点先进入可执行层，依赖满足后再进入下一层。

这样一来，互不依赖的节点可以并行启动，有依赖的节点不会抢跑。

### 第二步：为每个组件分配执行线程

每个组件可以配置自己的并发数。引擎把所有组件的并发数相加，创建一个固定大小的线程池，然后为每个组件的每一份并发提交一个执行任务。

组件的并发不是「多开几个线程读同一张表」这么简单。它意味着同一个组件会有多个工作线程同时消费上游队列、同时向下游写数据，因此组件内部的表元数据缓存、批量写入、状态更新都需要考虑线程安全。

### 第三步：为每条连线创建有界队列

连线在运行时对应一条有界阻塞队列，默认容量是 10 个批次，也可以按连线单独配置，并设有容量上限防止误配置撑爆内存。

有界队列带来的直接效果是**背压**：当下游处理不过来，队列被填满，上游继续写入时就会阻塞，而不是无限堆内存。流任务可以跑很久，靠的不是「内存足够大」，而是「队列足够小且能挡住上游」。

同一个源节点到同一个目标节点的多条连线会共用一条队列，容量取其中的最大值，避免同一对节点之间出现多份重复缓冲。

### 第四步：源节点发出起始信号

源组件没有上游队列，引擎会给它一个带起始标记的空 FlowFile，触发它开始工作。从这一刻起，源组件进入自己的读取循环：

- 批处理源：执行查询，按批读取结果集，读完发送结束标记；
- 增量源：在查询中带上水位条件，只读取水位之后的数据；
- CDC 源：启动日志采集器，持续把变更事件转换成 FlowFile；
- HTTP / 消息源：监听请求或消息，来一条处理一条。

### 第五步：批次在队列中流动

批次在队列中的流动过程如下：

```text
[Source] 读取一批数据
   │
   │ 数据 + 表结构 + 水位
   ▼
(有界队列) ◀── 队列满时上游阻塞，形成背压
   │
   ▼
[Operator] SQL / 脚本 / 字段转换
   │
   │ 产出新的 FlowFile
   ▼
(有界队列)
   │
   ▼
[Sink] 批量写入目标表
   │
   │ 写入成功
   ▼
[状态存储] 提交水位 / 位点
```

### 第六步：结束信号沿图传播

源组件读完后，会向下游发送一个带结束标记的 FlowFile。下游组件收到后并不是立刻退出，而是要等所有上游都发送结束标记，才认为自己可以结束；处理完手头的数据后，再把结束标记继续传给下一层。

这保证了「上游读完」和「下游写完」之间不会出现半截数据。对于有多个上游的组件，结束信号还起到了**汇合屏障**的作用：所有输入都到齐，才算这一轮结束。

### 第七步：Sink 提交状态

当 FlowFile 携带状态，并且当前组件是 Sink（或者没有下游）时，组件会把状态合并进执行上下文并持久化。

这一步非常关键。它把「数据写入成功」和「位点推进」绑定在同一条链路上：数据没写成功，位点不会提前提交；位点提交了，说明这批数据已经落到目标端。

## 05 流批一体的分界线：源决定时间，下游只认批次

DataY 的流批统一，不是把批任务伪装成流任务，也不是让流任务跑一遍就退出，而是把差异收敛到**源组件的数据边界**上。

把两条路径并排画出来，差异只在源头和终点：

```text
批处理：有限数据
[源表 / 文件] ──▶ [分批读取] ──▶ [逐批处理] ──▶ [逐批写入] ──▶ [结束标记] ──▶ 任务收尾

流处理：无限变化
[CDC / HTTP / 消息] ──▶ [持续产生批次] ──▶ [逐批处理] ──▶ [逐批写入] ──▶ 长期运行（直到停止）

                        中间环节共用同一套 Operator 和 Sink
```

对下游来说，两种模式没有本质区别：都是「从队列里拿一个 FlowFile，处理，再交给下游」。真正的差异只有三点：

1. **数据有没有终点**。批处理源读完后发结束标记，整张图可以收尾；流处理源长期不结束，整张图持续运行。
2. **状态怎么推进**。批处理用增量字段的最大值作为水位；CDC 用 binlog 位点、WAL LSN 或 resume token 作为位点。
3. **失败后从哪儿开始**。批处理从上次水位继续；CDC 从上次提交的位点继续。两者最终都落在同一套状态存储里。

DataY 把这三种典型形态放在同一张表里看，会更清楚：

| 形态 | 数据边界 | 推进依据 | 结束条件 | 典型组件 |
| --- | --- | --- | --- | --- |
| 全量批处理 | 当前表的全部数据 | 无，或一次性水位 | 源读完，结束信号传到底 | JDBC 流式输入、文件输入 |
| 增量批处理 | 水位之后的新数据 | 增量字段最大值 | 本轮新数据读完 | JDBC 流式输入 + 增量字段 |
| CDC 实时同步 | 持续到达的变更事件 | binlog 位点 / LSN / token | 人为停止或故障 | MySQL / PostgreSQL / Oracle / 达梦 / SQL Server / MongoDB CDC |
| 事件驱动 | 每次请求或消息 | 请求本身或消费位点 | 人为停止 | HTTP 监听、Kafka、MQTT |

这张表里的「处理」和「写入」两列是共享的。也就是说，你可以把一条批处理链路的 Sink 原封不动地接到 CDC Source 后面，也可以把 CDC 链路临时改成按水位补数。**组件不需要为流批各写一份。**

## 06 批处理路径：把大结果集拆成可控的小批次

批处理最怕两件事：一次性把结果集读进内存，以及把整张表塞进一条 SQL 事务。

DataY 的做法是「流式读、分批走、批量写」，数据流如下：

```text
[源库查询]
    │
    ▼
[流式结果集] 边读边处理
    │
    │ 每读满一批（默认约 1 万行）
    ▼
[FlowFile] 批次 + 表结构
    │
    ▼
(有界队列)
    │
    ▼
[字段映射 / SQL 加工]
    │
    ▼
[自动建表 / 类型转换] ──▶ [批量写入目标]
```

几个关键点：

- **结果集是流式读取的**，不是先全部加载到内存再处理。驱动按 fetch size 从服务端拉取，内存占用与结果集总大小解耦。
- **每批封装成 FlowFile**，批大小可以按组件配置。批太大，单次处理慢、内存高；批太小，调度和写入开销大。
- **表结构随批次传递**。源表的字段名、字段类型、库表信息会跟着数据一起走，Sink 不需要再回源库查一遍元数据。
- **自动建表与类型转换**。目标表不存在时，根据源表元数据生成目标端 DDL；不同数据库的类型差异由转换层处理。源表加字段后，下游可以跟着识别。
- **批量写入**。关系库走 JDBC 批处理，DuckDB 走 Appender，Doris 走 Stream Load。不同目标用各自最合适的写入方式，而不是统一拼 SQL。

当任务需要做聚合、关联或复杂清洗时，可以把数据先落到任务内的 DuckDB 临时库，用 SQL 完成计算，再把结果批次发往下游。此时 Operator 扮演的是一个「微批计算节点」：一批数据进来，DuckDB 算完，一批结果出去。

## 07 流处理路径：CDC 的快照、增量与事件合并

CDC 是流批一体里最能体现设计功力的部分。因为它同时包含「全量」和「增量」两种语义，而且必须在同一个任务里无缝衔接。

一条典型的 CDC 链路包含四段，整条数据流如下：

```text
[首次启动]
    │
    ▼
[记录当前位点]
    │
    ▼
[一致性快照] 可重复读事务
    │
    │ 按 INSERT 事件分批
    ▼
[从记录的位点启动增量采集]
    │
    ▼
[Binlog / WAL / LogMiner] 持续产生变更
    │
    │ 同表同类型事件合并（最多 1 万条）
    ▼
[FlowFile] 事件类型 + 表结构 + 位点
    │
    ▼
[Sink 写入目标]
    │
    │ 写入成功
    ▼
[提交位点] 本地文件 / MinIO
```

下面按顺序展开。

### 先全量，再增量

首次启动且没有历史位点时，CDC 源会先记录当前的日志位点，然后在一致性事务中读取历史全量数据，按 INSERT 事件分批下发。快照读完后，再从刚才记录的位点开始消费增量。

这个顺序很重要：**先记位点，再读快照**。快照期间发生的变更不会被漏掉，因为增量会从快照开始前的位点补放。代价是快照窗口内的变更可能被重复应用，所以下游写入需要具备幂等能力。

快照完成标记和起始位点会一起持久化。如果两者分开保存，任务在「快照已完成、位点还没落盘」的窗口里崩溃，重启后就可能误判为没有位点，从而丢掉一段变更。

### 事件合并，减少下游压力

Binlog 里的变更是一条条事件。如果每来一条就往下游发一个 FlowFile，下游会被大量小批次拖垮。

DataY 在 CDC 源和下游之间做了一层合并：**同一张表、同一种事件类型**的相邻事件会先攒在缓冲区里，达到一定数量或遇到不同类型的事件时，再合并成一个 FlowFile 下发。合并上限是一万条。

合并后的 FlowFile 会带上事件类型、库表信息、表结构和位点。下游可以根据事件类型决定写入策略：

- INSERT：插入或 upsert；
- UPDATE：按主键更新，或整行覆盖；
- DELETE：按主键删除；
- 也可以只处理某几类事件，忽略不需要的变更。

### 位点只在下游成功后推进

CDC 的位点不是采集器自己提交的，而是放在 FlowFile 的状态里，跟着数据流到 Sink。Sink 写完这一批，才把位点合并进上下文并持久化。

这带来的是 **at-least-once** 语义：下游失败时位点不推进，重启后从上次成功的位置重放；下游成功但状态提交前崩溃，重启后可能重复一小段。对于数据集成场景，这通常比「丢数据」更可接受，前提是 Sink 侧用主键 upsert、MERGE 或幂等删除来消化重复。

## 08 DuckDB 在链路中的位置：不只是目标库

很多人把 DuckDB 理解成「一个嵌入式分析数据库」。在 DataY 里，它的角色更多。

从数据流上看，DuckDB 位于 Source 和下游 Sink 之间：

```text
[Source 批次]
      │ Appender 批量写入
      ▼
[DuckDB 临时表]
      │ SQL
      ▼
[过滤 / 聚合 / 关联 / 窗口]
      │
      ▼
[结果批次]
      ├──▶ [写回关系库]
      ├──▶ [写入 DuckLake]
      ├──▶ [写入 Doris / ClickHouse]
      └──▶ [留在 DuckDB 供查询]
```

第一，它是**任务内的临时计算库**。每个任务实例可以有自己独立的 DuckDB 库文件，任务结束后清理。批次数据先落到临时表，再用 SQL 做加工，避免在 JVM 里手写复杂的聚合逻辑。

第二，它是**列式计算的加速器**。DuckDB 的列式存储、向量化执行和多线程能力，让单机也能处理不小规模的分析型计算。对于「2 核 4G 也能跑通全链路」这个目标来说，它比引入一套分布式引擎更现实。

第三，它是**数据湖的入口**。通过 DuckLake，数据可以按开放表格式写到对象存储，形成低成本的数据湖；需要更大规模查询时，再把结果外挂到 Doris、ClickHouse 等分析引擎。

第四，它是**批流共用的计算底座**。批处理用它做聚合，流处理的微批也用它做聚合。同一段 SQL 逻辑，不需要为流批各实现一遍。

需要说清楚的是：DuckDB 是单机引擎，不是分布式数仓。DataY 的定位也不是替代 Flink、Spark 或 Doris 集群，而是在「数据集成 + 轻量计算」这个区间里，用尽量少的组件把链路跑通。

## 09 可靠性：状态、失败与恢复

DataY 的可靠性模型可以概括成三句话：

**第一，状态跟着数据走。** 增量水位、CDC 位点、消费 offset 都放在 FlowFile 里，而不是采集器自己的内存里。

**第二，状态在 Sink 提交。** 只有数据写入成功，Sink 才把状态合并进执行上下文并持久化。状态存储支持本地文件和 MinIO，单机与集群用同一套接口。

**第三，失败就整图取消。** 任何一个组件抛出异常，引擎会标记失败、停止所有组件、中断线程池，并让任务以失败结束。不会出现「上游还在读、下游已经死了」的假运行状态。

把这条恢复链路串起来看：

```text
[任务启动]
    │
    ▼
[加载历史状态]
    │
    ▼
[从水位 / 位点继续]
    │
    ▼
[正常处理]
    │
    ├──────────────┐
    │ 写入成功      │ 组件异常
    ▼              ▼
[Sink 提交状态]  [取消全部组件]
    │              │
    ▼              ▼
[任务成功]      [任务失败]
                   │
                   ▼
          [调度层重试 / 人工处理]
                   │
                   └──▶ 回到任务启动
```

这套模型有几个边界需要明确：

- 它是 **at-least-once**，不是 exactly-once。重复由 Sink 的幂等写入消化。
- 它不负责 Cron 和重试策略。DataY 只负责执行一张 DAG；定时、依赖、失败重试由上层调度系统负责。
- 它不会在任务失败时自动「跳过坏数据继续跑」。是否忽略错误，由组件配置显式决定。
- 调试模式不会读写正式状态，也不会真正写目标库，避免调试污染生产水位。

## 10 性能与资源：把内存花在刀刃上

DataY 的性能设计没有太多花哨的技巧，核心是「限制」和「批量化」。

**限制队列。** 每条连线都是有界队列，下游慢就把上游挡住。流任务可以长期运行，不是因为内存无限，而是因为缓冲有上限。

**限制批次。** 数据按批读取、按批传递、按批写入。单批大小可配，避免一次处理过多数据导致 GC 抖动或事务过大。

**流式读取。** 源库结果集按 fetch size 拉取，不在 JVM 里物化整个结果集。

**并行执行。** 组件可以配置并发数，互不依赖的节点可以同时运行，一条数据流可以分出多条支路。

**用对写入方式。** JDBC 批处理、DuckDB Appender、Doris Stream Load，各自走最适合的通道，而不是一律拼 INSERT。

**把计算下推。** 能在 SQL 里完成的过滤、聚合、关联，就交给 DuckDB 的向量化引擎，而不是在 Java 里逐行处理。

这些设计叠加起来，才有了「一个 JAR、2 核 4G 跑通数据集成到报表查询」的可能性。它不是靠某个单点优化，而是靠整条链路的资源使用都可预期。

## 11 可扩展性：组件是积木，不是写死的流程

DataY 的组件不是硬编码在任务里的。引擎启动时会扫描组件实现，把组件编码、名称、分组、描述和配置字段注册到组件工厂；外部插件 JAR 也可以按同一套机制加载。

这意味着扩展一个新数据源，通常只需要实现一个组件，声明它的输入输出和配置项，不需要改引擎主干。对于企业内部的专有系统、行业协议或自定义写入逻辑，这一点比「支持多少种数据源」更重要。

除了数据源，链路里还可以插入：

- **SQL 组件**：做微批计算、聚合、关联；
- **脚本组件**：处理特殊字段、调用内部服务；
- **路由组件**：按 Hash 或随机策略把数据分流到不同下游；
- **模型组件**：按行调用大模型或决策服务，做实时打标、分类、决策；
- **质量组件**：在链路中做校验、拦截和告警。

这些组件共享同一套 FlowFile 模型和队列机制，因此可以自由组合。批任务里能用的算子，流任务里也能用；流任务里的 CDC 源，也可以接到批处理常用的 Sink 上。

## 12 适合什么，不适合什么

DataY 的流批一体，准确说是**数据集成层面的流批一体**。它适合这样的场景：

- 数据库到数据库的全量、增量同步；
- MySQL / PostgreSQL / Oracle / 达梦 / SQL Server / MongoDB 的 CDC 实时同步；
- CDC 数据实时落到 DuckDB、DuckLake，构建轻量实时数仓或数据湖；
- 文件、HTTP、飞书、Kafka、MQTT 等异构数据接入；
- 链路中的轻量 SQL 清洗、字段映射、路由和实时决策；

它不适合这样的场景：

- 需要事件时间窗口、复杂 CEP、超大规模有状态 Join 的流计算；
- 需要 exactly-once 端到端事务的强一致场景；
- 需要成百上千节点横向扩展的分布式计算；
- 需要长期保存大量中间状态、支持任意时间点回放的流处理平台。

把这些边界说清楚，不是削弱「流批一体」，而是让它可以被正确使用。工程上的成熟，往往不是「什么都能做」，而是「知道自己该做什么」。

## 13 结语：统一的不是接口，是数据流的生命线

回到开头的问题：流批一体到底统一了什么？

DataY 的答案是：

- 统一了**数据单位**：FlowFile 既是批次的信封，也是流中的事件；
- 统一了**执行模型**：组件、队列、线程、结束信号，批和流共用一套；
- 统一了**状态语义**：水位和位点跟着数据走，在 Sink 处提交；
- 统一了**组件生态**：同一个 Source、Operator、Sink，可以出现在不同时间尺度的链路里；
- 统一了**运维方式**：一张 DAG、一套日志、一套状态存储。

批处理关心「把数据搬完」，流处理关心「把变化接住」。当两者共享同一条数据流的生命线，切换成本就不再是「换一套引擎」，而只是「换一个源，换一种结束条件」。

这大概就是轻量引擎最务实的样子：不追求大而全，而是把一条链路做顺，让数据从进入系统到产生价值，中间少几次折腾。
