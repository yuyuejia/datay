# 4 分钟变 17 秒：DataY 的 DuckLake 写入优化是怎么做的

> 400 万行、约 1GB 数据，同一台机器、同一份数据。
> 不换引擎，不加机器，只把写入路径上的一段“无用功”拿掉。

---

## 01 一条 1GB 的同步任务，为什么跑了 4 分钟

我们用一个很常见的场景做验证：

- 源端：MySQL 9.4.0，一张 400 万行、约 1064 MB 的明细表；
- 目标端：DuckLake，本地数据目录；
- 链路：DataY 的 MySQL 到 DuckLake 全量同步，每 10000 行一个批次。

源表有 13 列，其中一列是 224 字符的文本，整表文本字符数约 8.96 亿。数据不算小，但也绝对不算“大到写不动”。

优化前，端到端跑完需要：

- 总耗时：242.6 秒；
- 写入吞吐：16,487 行/秒；
- 源侧吞吐：4.4 MB/s。

4 分钟才写完 1GB，已经很难叫“同步”了，更像是“慢慢灌”。

而且 CPU 没跑满，磁盘也没跑满。

时间到底花在哪了？

---

## 02 慢在哪：数据绕了一圈 SQL

问题不在 DuckLake，而在“把数据拼成 SQL”这件事。

优化前的写入方式很直接：每 10000 行拼成一条巨大的插入语句，再交给 DuckDB 执行。

一批 13 列、每行还带 224 字符文本的数据，单条 SQL 轻松到几 MB。

这条 SQL 进入数据库后，要走完整流程：

> 数据 → SQL 文本 → 解析 → 绑定 → 生成执行计划 → 执行 → 写入

对于一个普通的批量导入，这条路线本身没有问题。

但问题在于：**每一行数据都被当成 SQL 表达式重新解析、重新绑定、重新规划。**

字符串要转义，空值要判断，金额要保精度，时间类型要转换；一批一万行，就是一万份“表达式”的解析和绑定工作。

同时，几 MB 的 SQL 文本还要在 JVM 里一点点拼接，数据量越大，字符串越长，垃圾回收压力也越大。

所以真正的瓶颈是：

> **数据本来就在内存里，却要先变成 SQL，再让数据库解析回数据。**

这一段来回折腾，才是那 4 分钟的主要来源。

---

## 03 换一种写法：直接追加，而不是逐行解析

DuckDB 提供了一个面向批量写入的接口：Appender。

它不拼 SQL，也不走解析、绑定、优化这一整套流程，而是把数据按列直接追加到目标表。

可以把它理解成三步：

1. 打开目标表的写入通道；
2. 逐行开始、按目标列顺序追加值、结束一行；
3. 关闭通道，完成本批写入。

对比一下两条路径：

> 旧路径：数据 → 拼 SQL → 解析 → 规划 → 再变回数据 → 写入
>
> 新路径：数据 → Appender → 写入

少了中间那一大圈转换，收益非常直接。

同时，快并不意味着牺牲精度。金额的小数位、时间戳、布尔值，仍然会按目标列类型做归一化处理，不会因为换了写入通道就把 12.34 写成 1234。

在 1M 行、12 列的本地微基准里，几种写入方式的差距很直观：

| 写入方式 | 吞吐（行/秒） | 说明 |
|---|---:|---|
| 多值插入，1000 行/批 | 约 31,500 | 解析与规划成本高 |
| Appender，1000 行/批 | 约 164,220 | 绕过 SQL 层 |
| Appender，10000 行/批 | 约 411,409 | 批越大，收益越明显 |
| Appender 加临时表中转 | 约 750,245 | 文件更少，但实现更重 |

微基准只测“写入”本身。真实链路还要读 MySQL、做类型转换、组装数据，所以端到端会低一些。

但方向已经很清楚：

> **把 SQL 从写入热路径上拿掉，收益是数量级的。**

---

## 04 快之外，更重要的是别写错

如果故事到这里结束，会留下一个很大的坑。

DuckLake 是湖仓格式，没有主键，也没有唯一约束。它的写入语义和普通关系型数据库不一样：

- 新增、追加、覆盖：适合走 Appender；
- 更新、删除：需要定位旧数据、重写数据文件，必须走 SQL；
- CDC 场景里的更新，还依赖“变更前镜像”来判断更新范围。

如果把更新也塞进 Appender，会发生什么？

Appender 只负责“追加一行”，它不知道什么是更新。结果就是：

> 原本要更新 1 行 → 实际追加 1 行 → 表里变成 2 行 → 数据重复，而且很难事后发现。

所以实现里明确了一条规则：

> **只有新增、追加、覆盖三类写入允许使用 Appender。**
>
> **更新、删除、替换继续走原来的 SQL 路径。**

这条“更新保护”不是保守，而是底线：

> **性能优化不能改变数据语义。**

---

## 05 回退也要有边界

除了事件类型，还要处理 Appender 本身不可用的情况。

比如当前连接不是原生 DuckDB 连接、目标表或元数据目录不存在、写入通道创建失败。

这些情况要能回退到原来的批量插入，否则一个边缘场景就会让整条链路失败。

但回退有一个前提：**必须确认一行都还没写。**

于是实现里把结果分成两种：

- 还没开始写：返回“不可用”，调用方安全回退到批量插入；
- 已经进入写行阶段：直接报错，不回退、不重试当前批次。

一句话总结：

> **没开始写，可以退；已经开始写，宁可失败，也不能重复。**

---

## 06 一处能力，两条链路复用

这次优化没有只改一个组件，而是把 Appender 能力收敛成了一处公共实现。

它负责四件事：

- 判断事件类型，只放行新增、追加、覆盖；
- 识别连接类型，兼容连接池代理和原生连接；
- 定位目标表，支持 DuckLake 的 catalog、schema、table；
- 处理列映射、类型归一化，以及回退和“部分写入”语义。

然后，两个写入入口共用这套能力：

> 批量迁移写入：优先走 Appender；
>
> 通用 JDBC 输出：经数据源适配层判断后，同样走 Appender。

这样做的好处是：

- 两条链路的行为完全一致，不会一个能回退、一个不能；
- 普通 DuckDB 不受影响，只有 DuckLake 在追加类事件上放行；
- 字段映射继续生效，用户不需要改任何配置。

对使用者来说，这次优化是“无感”的：

> 还是原来的同步任务，还是原来的目标表，只是写得更快了。

## 07 实测：400 万行 / 1GB，17 秒

同一份数据、同一台机器（Apple M5，10 核，24GB），只切换写入路径：

| 指标 | 优化前：多值插入 | 优化后：Appender |
|---|---:|---:|
| 总耗时 | 242.6 秒 | **16.8 秒** |
| 写入吞吐 | 16,487 行/秒 | **237,764 行/秒** |
| 源侧吞吐 | 4.4 MB/s | **63.2 MB/s** |
| 相对提升 | 1 倍 | **约 14.4 倍** |

多次运行在 16.8 秒到 17.4 秒之间，吞吐约 23 万到 23.8 万行/秒，波动主要来自本机 MySQL 读取和 JVM 状态。

### 数据对不对？

快不是全部，写完还要能对上：

| 校验项 | 结果 |
|---|---|
| 目标表行数 | 4,000,000，与源表一致 |
| 主键去重数 | 4,000,000，无重复 |
| 文本字符总数 | 896,000,000，与源表一致 |
| 抽样 3 行关键字段 | 订单号、金额、状态、时间、文本全部一致 |

### 写完之后好不好查？

DuckLake 输出总大小约 332 MB，其中 Parquet 数据约 328 MB。

全表行数统计 0.19 秒，按状态分组聚合 0.067 秒。

源数据 1GB，写入后约 330MB，查询延迟在百毫秒级。对于一份 400 万行的明细表，这个结果可以直接拿去用。

## 08 也要说清楚代价和边界

Appender 不是“所有写入问题的答案”。

### 1. 更新仍然慢

DuckLake 的更新需要重写数据文件。CDC 场景里，一行更新可能牵动整个文件，吞吐远低于追加写入。

所以这次只优化了追加类事件，更新保持 SQL 路径，不制造“看起来很快、实际写错”的假象。

### 2. 小批次收益有限

Appender 的优势在批量。如果每批只有几十行，打开和关闭写入通道的固定成本会吃掉大部分收益。

当前链路默认 10000 行一个批次，正好落在一个比较舒服的区间。

### 3. 文件数量会变多

这次实测输出了约 2000 个 Parquet 文件。原因是 Appender 内部会按批刷写，每一次刷写落在 DuckLake 里就是一次数据文件写入。

在当前查询规模下，2000 个文件的全表扫描仍然只有 0.19 秒，不是瓶颈。

但如果数据量继续增长，或者跑在对象存储上，单文件过小会带来额外的元数据和请求开销。后续可以评估：

- 用临时表中转，再按批合并写入；
- 调大单次提交的数据量；
- 配合 DuckLake 的 compaction 合并小文件。

### 4. 不是所有数据库都适用

Appender 是 DuckDB 的能力。

MySQL、PostgreSQL、Oracle 这些目标库，仍然要走各自的批量写入优化路径。这次改动只影响 DuckDB 和 DuckLake，没有改变其他数据源的行为。

---

## 09 写在最后

这次优化没有换引擎，没有加机器，也没有把并发拉满。

只是把写入热路径上的一段“无用功”拿掉了：

> 数据 → SQL 文本 → 解析 → 规划 → 再变回数据

换成：

> 数据 → Appender → 存储

性能优化的很多收益，最后都来自这种“看起来理所当然、其实一直在绕路”的地方。

但比“快 14 倍”更重要的是，这次改动同时守住了三条线：

- **语义正确**：更新、删除不走 Appender；
- **失败可控**：没写可以回退，写了就不重复；
- **结果可信**：行数、去重、抽样值逐项对上。

> **先把边界想清楚，再谈性能。**
>
> **能安全地快，才是真的快。**

## DataY 轻量数据平台

**DataY 是一套开源、轻量的一体化数据平台**，理念很简单：

> 数据平台可以很小，功能不打折。

传统数据平台往往需要 Hadoop、Spark、Flink、ClickHouse 一整套组件，几十台机器起步，运维门槛高。DataY 选择另一条路：

- **一个 JAR**，自研流批一体数据集成引擎，拒绝组件地狱；
- **2 核 4G** 就能跑通「数据集成 → 数据建模 → 数据开发 → 任务调度 → 数据应用」的完整链路；
- 零依赖启动，10 分钟搭好开发环境；
- 内嵌 DuckDB 作为高性能分析引擎，同时支持 Doris、ClickHouse 等外部分析引擎；
- 调度 master 与执行 worker 可分可合，单机和集群同一套代码。

这里的「轻量」指的是**运行资源门槛低**，不是能力轻量。

DataY 由两块组成：

| 模块 | 定位 | 说明 |
| --- | --- | --- |
| **DataY Core** | 数据集成引擎 | 轻量、可嵌入、可扩展、流批一体；JSON 定义任务、自动建表、CDC 实时同步；可脱离 Web 独立运行或嵌入 Java 应用 |
| **DataY Web** | 可视化数据平台 | 拖拽式任务设计、任务调度、维度建模、指标管理、智能问数、分析看板 |

平台的核心能力包括：

- **数据集成**：MySQL、PostgreSQL、Oracle、SQL Server、Doris、ClickHouse、DuckDB 等二十余种数据源，支持全量、增量与 CDC 实时同步；
- **维度建模**：星型 / 雪花模型，普通维度、层级维度、时间维度，事实表外键一键关联；
- **任务调度**：Quartz Cron 精确到秒，DAG 工作流编排，失败重试与暂停恢复；
- **高性能数仓**：内嵌 DuckDB，列存 + 向量化，支持 DuckLake 数据湖，也可外挂 Doris / ClickHouse；
- **智能问数**：自然语言 → 指标 → 维度 → 时间过滤 → 取数，一句话拿报表；
- **分析看板**：数据集管理、AI 生成看板、24 栅格设计器、大屏与嵌入分享；
- **AI 原生能力**：AI SQL 查询助手、ETL 任务设计助手、看板设计助手、智能问数助手、Java 脚本助手，以及面向 Agent 的 MCP Harness。

AI 能力兼容 OpenAI Chat Completions 协议，OpenAI、DeepSeek、通义千问、Ollama 等模型服务都可以对接。默认使用 DeepSeek，启动时通过 `DATAY_AI_API_KEY` 配置即可。
