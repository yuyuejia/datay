# 一条数据流，如何自动分叉？——用「属性路由」把数据送到该去的地方

> 订单要按渠道分别入库、CDC 变更要按事件类型走不同处理、日志要按级别分流……
> 这些「同源不同目的地」的需求，本该是数据管道里一个节点就能解决的事。

---

## 一、一个几乎每个数据团队都遇到过的需求

先看一个很常见的场景。

某电商平台，所有订单都从同一个业务库同步过来。但对下游来说，这些订单**不是一路货**：

- **平台订单**（天猫 / 京东 / 抖音）要进平台对账库；
- **自营订单**（小程序 / App）要进自营订单表；
- **线下门店订单**要单独进门店系统；
- 还有一类**渠道未知**的脏数据，要单独捞出来给运营排查。

数据同学一开始的做法是这样的：

> 写三个同步任务，每个任务一条 SQL，靠 `WHERE channel = 'xxx'` 把数据分开。

能跑，但很快就开始难受：

1. **任务数量翻倍**。一个源要分四路，就是四个任务，四份连接配置、四套调度、四处日志；
2. **源库压力翻倍**。同一个表被重复扫了四遍，增量同步还要各自维护水位；
3. **口径容易跑偏**。新增一个渠道，得改四份 SQL；漏改一个，数据就悄悄少了一路；
4. **脏数据没人管**。忘写兜底逻辑，未知渠道的订单直接消失，出问题都查不到。

本质上，大家想要的东西很简单：

> **一份数据读进来，按规则自动分叉，各走各的下游。**

这恰恰是数据流引擎里 **路由（Router）** 这个角色该干的事。

---

## 二、路由和「随机分发」不是一回事

DataY Core 里早就有两个路由组件：`HashRouter` 和 `RandomRouter`。它们解决的是"**把数据摊开**"的问题——哈希打散、随机分发，用来做负载均衡或并行处理。

但上面那个场景要的不是"摊开"，而是"**按业务规则送到指定的地方**"：

| 需求 | Hash / Random | 属性路由 |
| --- | --- | --- |
| 把数据平均/随机分发 | ✅ | ❌ |
| 按字段值决定去向 | ❌ | ✅ |
| 去向由谁决定 | 引擎内部 | **连线标签**（业务自己定） |
| 未匹配的数据 | 不区分 | 走 `other` 兜底 |

所以我们补上了第三个路由组件：**`RouteOnAttribute`（属性路由）**。

它的核心思想一句话说清：

> **在连线上写标签，让数据自己找路。**

---

## 三、它是怎么工作的

普通组件的写法是"一个上游 → 多个下游"，数据会被**广播**到所有下游。而属性路由会在发送前，先判断这条 FlowFile 该去哪：

1. 读取 FlowFile 的属性 / 字段值；
2. 和每条下游连线的**标签**比对；
3. 只把数据发给命中的那条连线；
4. 没命中的，走标签为 `other` 的兜底连线。

标签在画布上是这样设置的：**双击连线，输入一个词**。这个词就是分流规则。

```
                     ┌── label: 自营  ──▶  自营订单表
 订单数据 ──▶ 属性路由 ├── label: 平台  ──▶  平台对账库
                     └── label: other ──▶  异常/脏数据表
```

它支持三种匹配方式，覆盖了绝大多数分流诉求。

---

## 四、三种匹配方式，各管一类事

### ① 按属性名匹配（默认）

> FlowFile 里**存在某个属性**，就去对应标签的连线。

适合上游已经打过标记的情况。比如 CDC 组件会在 FlowFile 上挂一个 `_eventType` 属性，你想让 `INSERT` 和 `DELETE` 走不同的处理逻辑，就可以用属性名匹配。

```json
{ "matchMode": "attribute" }
```

### ② 按属性值匹配

> 取**指定属性的值**，等于哪个标签就走哪条线。

适合分类值存在属性里的场景。

```json
{ "matchMode": "value", "attributeName": "channel" }
```

FlowFile 属性 `channel=平台`，就会自动进入标签为 `平台` 的连线。

### ③ 按数据项匹配（重点）

前两种是"整个 FlowFile 一起走"。但真实业务里，经常是**一个批次里混着不同类别的记录**：

```json
[
  { "order_id": 1001, "channel": "平台", "amount": 199 },
  { "order_id": 1002, "channel": "自营", "amount": 88 },
  { "order_id": 1003, "channel": "平台", "amount": 350 },
  { "order_id": 1004, "channel": "未知", "amount": 12 }
]
```

这时候就该用**数据项模式**：逐条看记录里的字段，命中哪条连线就分到哪条，**一个批次自动拆成多路**。

```json
{ "matchMode": "data", "dataField": "channel" }
```

上面这批数据会被拆成：

| 连线标签 | 收到的数据 |
| --- | --- |
| `平台` | `[{"order_id":1001,...},{"order_id":1003,...}]` |
| `自营` | `[{"order_id":1002,...}]` |
| `other` | `[{"order_id":1004,...}]` ← "未知"没命中，走兜底 |

拆分后每路数据**保留原有字段和属性**，下游组件可以像处理普通数据一样继续处理，完全无感。

---

## 五、`other` 兜底：别让脏数据悄悄消失

这是属性路由最值得说的一个设计。

传统 `WHERE` 过滤最怕的就是"**漏了一类值**"——上线时渠道只有三种，半年后业务加了第四种，过滤 SQL 没改，数据就凭空少了，还很难发现。

属性路由的兜底规则是：

> **所有未匹配的数据，自动进入标签为 `other` 的连线。**

于是你可以专门挂一个"异常数据"分支：落一张表、发个告警、或者只是记日志。**新增任何未知的类别，都不会再无声无息地丢掉。**

在画布上，这个分支长这样：

```
                     ┌── 平台  ──▶  平台对账库
 订单数据 ──▶ 属性路由 ├── 自营  ──▶  自营订单表
                     └── other ──▶  异常数据表（兜底 + 告警）
```

一条兜底连线，把"数据丢失"变成了"数据可观测"。

## 六、动手试一下：从生成数据到日志验证

下面用一个小任务验证属性路由的完整链路：**生成测试数据 → 按 `type` 分流 → 分别记日志**。

任务定义（Core 可直接运行的 JSON）：

```json
{
  "units": [
    {
      ".id": "gen1",
      ".name": "GenerateFlowFile",
      "inputData": "[{\"id\":1,\"type\":\"vip\"},{\"id\":2,\"type\":\"normal\"},{\"id\":3,\"type\":\"vip\"},{\"id\":4,\"type\":\"unknown\"}]",
      "dataFormat": "JSON_ARRAY",
      "loopCount": "1"
    },
    {
      ".id": "route1",
      ".name": "RouteOnAttribute",
      "matchMode": "data",
      "dataField": "type",
      "defaultLabel": "other"
    },
    { ".id": "log_vip", ".name": "LogFlowFile", "logDataContent": "true" },
    { ".id": "log_normal", ".name": "LogFlowFile", "logDataContent": "true" },
    { ".id": "log_other", ".name": "LogFlowFile", "logDataContent": "true" }
  ],
  "connections": [
    { "sourceId": "gen1", "targetId": "route1", "sourcePort": 0 },
    { "sourceId": "route1", "targetId": "log_vip", "sourcePort": 0, "label": "vip" },
    { "sourceId": "route1", "targetId": "log_normal", "sourcePort": 0, "label": "normal" },
    { "sourceId": "route1", "targetId": "log_other", "sourcePort": 0, "label": "other" }
  ],
  "version": "1.0.0"
}
```

运行后，日志里能清楚看到分流结果：

```
[LogFlowFile-log_vip]    ... 数据内容: [{"id":1,"type":"vip"},{"id":3,"type":"vip"}]
[LogFlowFile-log_normal] ... 数据内容: [{"id":2,"type":"normal"}]
[LogFlowFile-log_other]  ... 数据内容: [{"id":4,"type":"unknown"}]
```

- `vip` 的两条记录进了 `log_vip`；
- `normal` 进了 `log_normal`；
- **`unknown` 没命中任何标签，自动走了 `other` 兜底**。

这几种匹配方式在 DataY Web 的画布上操作更简单：拖一个「属性路由」节点，双击配好规则，再双击下游连线填上标签，保存即可。配完还能直接在节点的「调试」页跑一遍，肉眼确认每一路的数据对不对。

## 七、几个真实用法

属性路由只是个"分叉口"，但放到真实链路里，能省掉很多重复工作：

**① 一张表，按渠道/区域分库分表**
上游一次读取，下游按 `channel` 或 `region` 分别写入不同库表，源库只扫一次，增量水位只维护一份。

**② CDC 变更按事件类型分流**
`INSERT` / `UPDATE` / `DELETE` 走三条不同的处理逻辑：新增走同步、更新走 upsert、删除走逻辑删除。属性值模式即可搞定。

**③ 按日志级别/业务线分流**
批量日志按 `level` 或 `app` 字段拆开，`ERROR` 单独进告警通道，`other` 兜底接未定义级别。

**④ 脏数据隔离**
任何"没想过会出现"的新值，都会被 `other` 接住，不再污染主链路，也不再凭空消失。

## 八、DataY 是什么

上面这条分流链路跑在 **DataY** 上。它是一个**开源、轻量的一体化数据平台**：

> 一个 JAR、内嵌 DuckDB，**2 核 4G** 就能跑通「数据集成 → 数据建模 → 数据开发 → 任务调度 → 数据应用」的完整链路。

它由两块组成：

| 模块 | 定位 | 说明 |
| --- | --- | --- |
| **DataY Core** | 数据集成引擎 | 轻量、可嵌入、可扩展、流批一体；JSON 定义任务、自动建表、CDC 实时同步；可脱离 Web 独立运行或嵌入 Java 应用 |
| **DataY Web** | 可视化数据平台 | 拖拽式任务设计、任务调度、维度建模、指标管理、智能问数 |

**五大能力：**

- 🔌 **数据集成**：MySQL / PostgreSQL / Oracle / SQL Server / Doris / ClickHouse / DuckDB 等十余种数据源，支持 MySQL Binlog、PostgreSQL WAL CDC 实时同步，Kafka 消费，自动建表与 DDL 转换；
- 📐 **维度建模**：星型 / 雪花模型，普通维度、层级维度、时间维度，事实表外键一键关联；
- ⏰ **任务调度**：Quartz Cron 精确到秒，DAG 拓扑编排，父子任务依赖，失败重试；
- 🚀 **高性能数仓**：内嵌 DuckDB（列存 + 向量化），支持 DuckLake 数据湖，需要时外挂 Doris / ClickHouse；
- 🤖 **智能问数**：自然语言 → 指标 → 维度 → 时间过滤 → 取数，一句话拿报表。

## 九、写在最后

回到开头那个问题：**一份数据要分几路，这件事到底该由谁来做？**

过去它被塞进了 SQL、塞进了多个重复任务、塞进了调度配置里，于是每加一路都要动一遍管道。

其实它本该是管道里的一个"岔路口"：

> **读一次，分清楚，各走各的。去向由连线上的一句话决定，兜底由 `other` 接住。**

当"新增一类数据该去哪里"从"改四个任务"变成"双击连线填个标签"，数据管道才真正变得**可维护**。
