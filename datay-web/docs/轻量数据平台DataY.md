# DataY = DataX + Nifi + DolphinScheduler：一个 2 核 4G 的轻量数据平台，如何把技术栈做减法

> 过去几年，我们习惯用「堆组件」的方式解决数据问题：
> 同步用 DataX，编排用 Nifi，调度用 DolphinScheduler，计算用 Spark/Flink，存储用 Hive/HDFS，查询用 ClickHouse……
>
> 组件越堆越多，平台越来越重，最后发现：**真正被数据量难住的场景没多少，先被技术栈难住的团队倒不少。**
>
> DataY 想做的，是把这件事重新做一遍：**用一套自研的流批一体集成框架、一套自研的分布式调度、一个轻量数据湖，把 DataX + Nifi + DolphinScheduler 的能力收进一个 JAR。**

---

## 一、数据平台的「军备竞赛」，正在拖垮大多数团队

先看一张很多团队都似曾相识的架构清单：

| 环节 | 常见选型 | 背后还要带上 |
| --- | --- | --- |
| 数据同步 | DataX、Sqoop、Flink CDC | 任务机、调度器、驱动包、版本兼容 |
| 流程编排 | Nifi、Airflow | ZooKeeper、元数据库、Web 服务 |
| 任务调度 | DolphinScheduler、Azkaban | Master/Worker 集群、注册中心、告警 |
| 批流计算 | Spark、Flink | YARN/K8s、Checkpoint 存储、资源队列 |
| 数据存储 | HDFS、Hive、Hudi、Iceberg | NameNode、Metastore、小文件治理 |
| 查询分析 | ClickHouse、Doris、StarRocks | 多副本集群、扩容、慢查询治理 |
| 元数据/权限 | Atlas、Ranger | 又一套服务、又一套账号体系 |

这套架构本身没有错。**错的是把它当成所有团队的默认答案。**

大厂做这套东西，是因为数据量真的到了 PB 级、并发真的到了成百上千、组织真的需要隔离。但大量中小企业、业务部门、区域团队面对的是另一道题：

- 数据量在 GB 到几十 TB 之间；
- 时效要求是分钟级、小时级，而不是毫秒级；
- 用数的人不多，但每个人都希望「今天提需求，明天就能看数」；
- 团队里没有专职大数据工程师，更养不起一个平台运维组。

于是就会出现一种荒诞的对比：

> **业务数据只有 200G，平台组件先占了 200G 内存。**

这不是技术问题，是**架构错配**。

而错配的代价，远不止几台机器：

1. **部署复杂**：每个组件都有自己的安装方式、配置文件、版本矩阵和踩坑文档；
2. **链路断裂**：数据从 A 组件流到 B 组件，状态、权限、口径各存一份，出了问题很难端到端定位；
3. **资源浪费**：为了「高可用」，每个组件都至少三副本，小团队的实际负载却长期低于 10%；
4. **人才门槛高**：招一个能同时玩转 Spark、Flink、DolphinScheduler、Hive 的人，成本远高于业务本身；
5. **创新被拖慢**：想接一个 MySQL、做一个日报，先要过一遍平台立项、资源申请、组件选型。

**技术栈本该是手段，最后却成了目的。**

## 二、先想清楚：一个数据平台，到底需要几套技术栈？

把花哨的概念剥掉，数据平台的需求其实只有五句话：

1. **进得来**：把分散在各处的数据，稳定、增量、实时地接进来；
2. **算得动**：能清洗、关联、聚合，能按业务口径加工；
3. **调得准**：任务按时间、按依赖可靠地跑，失败能重试，状态可追踪；
4. **存得下**：有一个成本可控、查询够快的存储底座；
5. **用得上**：业务能自助取数，AI 能直接理解和操作。

这五件事，真的需要五套独立的技术栈吗？

DataY 的判断是：**不需要。**

我们给 DataY 的定位只有一句话：

> **DataY = DataX + Nifi + DolphinScheduler**

注意，这个「等于」不是把三个开源项目打包在一起，而是**用同一套运行时，重新实现这三类能力**：

- 像 DataX 一样把数据从源头搬到目标；
- 像 Nifi 一样用组件和连线编排数据流；
- 像 DolphinScheduler 一样做定时调度、依赖调度和实例管理。

区别在于：它们不再是三个进程、三套元数据、三种部署方式，而是**一个引擎、一个平台、一个 JAR**。

## 三、第一块积木：自研流批一体数据集成框架

DataY 的底座叫 **DataY Core**，它要解决的是「数据怎么进来、怎么加工、怎么出去」。

### 1. 用 DAG 描述数据流，而不是写一堆同步脚本

一个 DataY 任务，本质上是一张有向无环图：

```json
{
  "units": [
    { ".id": "in",  ".name": "MySQLBinlogInput", "table": "orders" },
    { ".id": "sql", ".name": "StreamSqlUnit",    "sql": "select * from orders where status = 'PAID'" },
    { ".id": "out", ".name": "DuckLakeWrite",    "table": "dwd_orders" }
  ],
  "connections": [
    { "sourceId": "in",  "targetId": "sql" },
    { "sourceId": "sql", "targetId": "out" }
  ]
}
```

- `units` 是组件，负责「读、算、写、路由」；
- `connections` 是连线，决定数据流向；
- 引擎负责拓扑排序、并发执行、队列传递、失败中断和状态恢复。

同一份任务定义，既可以在 Web 画布上拖出来，也可以作为 JSON 交给 Core 独立执行，或者嵌入到其他 Java 应用里。

### 2. 流和批，共用一套组件

很多平台的「流批一体」是两套引擎套一个壳：批走 Spark，流走 Flink，最后用调度器拼起来。

DataY 的做法更直接：**流和批从第一天就共用同一套组件模型和运行时。**

- 批处理：一次读取一段数据，跑完即结束；
- 流处理：CDC 组件持续产生变更事件，下游组件持续消费；
- 中间的 SQL 加工、字段转换、Join、路由、写入，全部复用同一批算子。

这意味着：

- 今天用 `StreamJdbcInput` 做全量同步，明天换成 `MySQLBinlogInput` 做实时同步，下游加工逻辑不用重写；
- 同一个 `StreamSqlUnit`，既能处理一批历史数据，也能处理持续的增量事件；
- 调试时可以用同一套画布、同一套日志、同一套状态管理。

### 3. 不是「能跑」，而是「跑得稳」

一个数据集成框架真正的难点，从来不是把数据读出来，而是这些工程细节：

- **背压**：上下游速度不一致时，用有界队列阻塞上游，而不是把内存打爆；
- **并发**：每个组件可以单独配置并发数，按算子瓶颈扩缩；
- **增量状态**：记录同步位点，失败后从断点恢复，而不是每次全量重跑；
- **自动建表**：源表结构变化时自动做 DDL 转换，减少手工维护；
- **状态存储**：单机用本地文件，集群用 MinIO 共享增量状态；
- **可观测**：每个组件的日志、处理条数、异常链都能定位到具体节点。

这些能力不性感，但决定了一个平台能不能上生产。

### 4. 内嵌 DuckDB，把「计算引擎」也省掉

传统链路里，数据同步完之后，还要把数据交给 Spark/Flink 做加工。DataY 直接把 **DuckDB** 嵌进引擎：

- 列式存储、向量化执行、多线程；
- 用标准 SQL 做清洗、关联、聚合；
- 不需要额外部署计算集群；
- 单机就能跑出足以覆盖大多数业务场景的性能。

于是，一套 DataY Core 同时承担了「DataX 的同步」和「Nifi 的编排」，还顺带把轻量计算做完了。

## 四、第二块积木：自研分布式调度，单机和集群同一套代码

数据进来了，下一步是「按时、按依赖、可靠地跑」。

DataY 的调度系统没有另起一套庞大集群，而是把调度能力做进了平台本身：

### 1. master / worker 分离，但不强制分离

通过一个配置项 `development.mode`，同一个程序可以扮演不同角色：

| 模式 | 调度 | 执行 | 依赖 Redis | 适用场景 |
| --- | --- | --- | --- | --- |
| `standalone` | 有 | 有 | 否 | 单机、开发、边缘节点 |
| `master` | 有 | 无 | 是 | 只做调度，多副本部署 |
| `worker` | 无 | 有 | 是 | 只做执行，水平扩展 |

**单机不需要 Redis，也不需要额外组件；需要扩容时，改一个配置就能拆成集群。** 同一套代码，不用维护两个版本。

### 2. Cron、DAG、依赖、重试，一个都不少

- Cron 定时调度，精确到秒；
- DAG 工作流编排，父子任务自动拓扑排序；
- 依赖未满足时进入 `WAITING`，由补偿任务定时恢复；
- 支持手动触发、上线/下线、停止、失败重跑；
- 实例状态全程跟踪：`APPENDING / RUNNING / WAITING / SUCCESSFUL / FAILED / TIMEOUT / INTERRUPTED`；
- 记录执行节点、开始/结束时间、执行消息。

底层用 Quartz 做时间触发内核，上面的分布式协调、角色编排、事件分发、依赖恢复全部自研。**该复用的复用，该自己掌控的自己掌控。**

### 3. 任务可以跑在容器里，和调度进程隔离

当 ETL 任务依赖复杂、内存占用大时，可以切换成 Docker 执行模式：

- 任务在独立容器中执行，跑完即销毁；
- 调度进程不被任务依赖和内存拖垮；
- 任务 jar、驱动目录、日志目录通过挂载共享；
- 仍然复用同一套任务定义和状态存储。

对小团队来说，这比维护一个 YARN 集群轻得多。

## 五、第三块积木：轻量数据湖，把 Hadoop 那一套也省掉

数据加工完，总得有个地方存。

传统方案是 HDFS + Hive Metastore + Hudi/Iceberg，再配 Spark 读写。这套组合能力很强，但组件多、运维重、小文件治理麻烦，对中小数据量并不划算。

DataY 的选择是：

### 1. DuckDB：单机上的「列式数仓」

- 进程内嵌，无需独立服务；
- 列存 + 向量化 + 多线程；
- 直接读 Parquet/CSV，也能挂载对象存储；
- 对 GB 到 TB 级分析场景，性能足够，部署成本几乎为零。

### 2. DuckLake：把数据湖做成「文件 + 目录」

DataY 支持写入 **DuckLake**：

- 数据以 Parquet 文件落在本地或对象存储（如 MinIO）；
- 元数据由 catalog 管理；
- 支持 `append / update / replace / overwrite` 等写入模式；
- 计算与存储解耦，存储可以按需扩展；
- 不需要 HDFS、不需要 Hive Metastore、不需要另起 Spark 集群。

对于「数据要留、查询要快、成本要低」的团队，这是一条比 Hadoop 轻得多的路径。

### 3. 需要更大规模时，随时外挂

DataY 不排斥更强的引擎：

- 需要高并发点查和实时分析，可以把结果流式加载到 Doris / ClickHouse；
- 需要更大规模的数据湖，可以继续用对象存储 + DuckLake；
- 需要接回传统数仓，也可以通过 JDBC 组件双向同步。

**轻量不是封闭，而是默认简单，需要时再长。**

## 六、三块积木拼起来：2 核 4G 跑通全链路

把集成、调度、存储拼在一起，DataY 的整体形态是这样：

```text
                    ┌─────────────────────────────────────────┐
                    │              DataY Web                  │
                    │  数据源 / ETL 画布 / 调度 / 建模 / 问数   │
                    └──────────────────┬──────────────────────┘
                                       │
                    ┌──────────────────▼──────────────────────┐
                    │              DataY Core                 │
                    │  流批一体组件 DAG · CDC · SQL · 自动建表  │
                    │  增量状态 · 背压 · 并发 · 失败恢复        │
                    └──────────────────┬──────────────────────┘
                                       │
              ┌────────────────────────┼────────────────────────┐
              │                        │                        │
     ┌────────▼────────┐     ┌─────────▼─────────┐    ┌────────▼────────┐
     │  业务数据库      │     │  内嵌 DuckDB      │    │   DuckLake      │
     │  MySQL/PG/Oracle │     │  轻量计算/数仓     │    │ Parquet + 对象存储│
     └─────────────────┘     └───────────────────┘    └─────────────────┘
```

部署只需要三步：

```bash
git clone https://github.com/yuyuejia/datay
cd datay
mvn clean package -DskipTests
java -jar datay-web/target/*.jar --DATAY_AI_API_KEY=sk-xxxxxxxxx
```

浏览器打开 `http://localhost:8080`，默认账号 `admin/admin`。

一套最小可用的数据平台，从「数据接入 → 数据加工 → 任务调度 → 数据建模 → 指标问数」的完整链路，**2 核 4G 就能跑起来**。

对比一下传统方案：

| 维度 | 传统组合 | DataY |
| --- | --- | --- |
| 组件数量 | 同步、编排、调度、计算、存储、查询各一套 | 一个 JAR，内嵌引擎与存储 |
| 最小资源 | 十几台机器、上百 GB 内存起步 | 2 核 4G |
| 部署方式 | 每个组件单独安装、配置、联调 | 一条命令启动 |
| 元数据 | 各组件各存一份 | 平台统一管理 |
| 扩容 | 每个组件分别扩 | 调度 master/worker 按角色扩，存储按需扩 |
| 运维门槛 | 需要专职大数据工程师 | 后端/数据开发即可维护 |

**技术栈做减法，能力做加法**，这是 DataY 最核心的设计哲学。

## 七、AI 原生：不是加一个聊天框，而是让 Agent 直接操作平台

如果说前面的三块积木解决的是「平台能不能轻」，那么 AI 原生解决的是「平台能不能被 AI 真正用起来」。

DataY 没有在右上角挂一个只会聊天的机器人，而是把 AI 放进三个位置：

### 1. 管道里的 AI：大模型成为一个数据算子

`LlmComponent` 是 ETL 画布上的一个普通节点，和 Join、Filter、SQL 同级：

- 按行调用 OpenAI 兼容接口；
- 模型返回 JSON，就把字段合并进当前行；
- 返回普通文本，就写入 `llm_result` 字段继续往下传；
- 支持重试、超时、并发控制。

于是「用户评价 → 问题分类 → 结构化字段 → 数仓事实表」可以是一条完整的流批一体管道，而不是「导出数据 → 调外部 AI 服务 → 再导回来」的断链流程。

### 2. 语义层的 AI：模型只翻译，不发明口径

智能问数答不准，通常不是模型不够强，而是数据侧缺少业务语义。

DataY 用**维度建模 + 指标管理**把口径沉淀下来：

- 维度：普通维度、层级维度、时间维度；
- 指标：原子指标绑定事实表，衍生指标用 `${指标编码}` 引用，业务限定固化条件；
- 问数时，模型只负责把自然语言翻译成「指标 + 维度 + 限定 + 时间范围」，SQL 由平台生成。

这样带来的直接结果是：**AI 问数、指标面板、报表，用的是同一套口径。**

### 3. 平台里的 AI：通过 MCP 让 Agent 直接操作平台

DataY 提供 MCP 端点 `/mcp/datay`，把平台对象和指标能力暴露给 Claude Desktop、Cursor 等 AI 客户端，工具覆盖：

- **数据源**：创建、更新、删除、测试连接、浏览 schema/表/字段、执行查询；
- **ETL 任务**：创建、更新、试跑、立即执行、上线/下线、查看实例；
- **数据模型**：创建维度/事实模型、保存字段、生成 DDL、物化落表；
- **指标**：指标清单、语义检索、维度取值、指标取数、指标增删改查。

一句话描述的任务，Agent 可以自己拆成调用序列：

```text
「把 MySQL 订单库接进来，建一个每天 2 点同步到 DuckLake 的 ETL 任务，
  先试跑看看数据，没问题再上线。」

datasource_create   → datasource_tables → datasource_columns
etl_task_create     → etl_task_debug    → etl_task_run
etl_task_instances  → etl_task_online
```

建模、落表、问数同样可以自动化：

```text
data_model_create → data_model_materialize → query_metric_data
```

### 4. 能力越大，边界越要清楚

让 Agent 操作平台，最怕的是「权限靠提示词」。DataY 的做法是把边界做进系统：

- **传输层鉴权**：Bearer Token，非法直接 401；
- **租户隔离**：`X-Tenant-Id` / `X-Tenant-Code` 校验归属，跨租户数据不可见；
- **数据权限**：复用页面同一套 RBAC 与行级范围；
- **写开关**：`allow-mutating-tools=false` 一键降级为只读，但问数不受影响；
- **不暴露任意 SQL**：指标问数只提供受控的查询工具，模型不能临时发明口径；
- **出参裁剪**：数据源永不返回密码，任务列表不返回完整设计图。

一句话总结：

> **模型负责翻译与推理，平台负责口径、权限、状态和幂等。**

这才是 AI 原生，而不是 AI 外挂。

## 八、DataY 的边界：它不是万能药

写到这里，必须说清楚 DataY 不适合什么：

- **PB 级数据湖仓**：如果你已经有成熟的大数据团队和 PB 级数据，继续用 Spark/Flink/Iceberg 体系更合适；
- **超大规模实时计算**：毫秒级、百万级并发的流计算，仍然应该交给 Flink 这类专业引擎；
- **强多租户、强隔离的大型集团平台**：需要更重的资源调度与治理体系，DataY 的轻量反而是约束。

DataY 真正适合的是：

- 中小企业、业务部门、区域团队的第一套数据平台；
- 需要快速把数据接进来、跑起来、看起来的项目；
- 边缘节点、开发测试环境、SaaS 产品的内嵌数据能力；
- 想用 AI Agent 自动化数据工程流程，但不想先养一个大数据团队的组织。

**我们不认为「轻」能取代「重」，但认为大多数团队一开始并不需要那么重。**

## 九、写在最后：把数据平台还给大多数人

过去十年，数据平台的能力一直在变强，但使用门槛也在变高。

我们见过太多团队，业务还没跑起来，先花了三个月搭平台；数据还没到 TB，先买了一堆服务器；报表还没做几张，先招了一个大数据团队。

DataY 想反着来：

- 能用一个 JAR 解决的，不拆成十个服务；
- 能用内嵌引擎解决的，不另起一个集群；
- 能用一套调度解决的，不引第三套协调系统；
- 能让 Agent 直接做的，不让用户点二十个页面。

**DataY = DataX + Nifi + DolphinScheduler**，但它不是三个工具的拼盘，而是把这三类能力重新设计成一套运行时：

- 自研流批一体数据集成框架，负责「进得来、算得动」；
- 自研分布式调度框架，负责「调得准、跑得稳」；
- 轻量数据湖 DuckLake，负责「存得下、查得快」；
- AI 原生能力，负责「用得上、可自动化」。
